## key
dod_research
## topic
Data-oriented compiler engineering and evidence-based per-phase performance targets (Rust focus), with a read-only spot-check of the Boon compiler for the matching anti-patterns
## findings
- system: Zig self-hosted compiler (Andrew Kelley, DOD rework PR #7920 / #8266) | technique: Tokens and AST stored as struct-of-arrays (MultiArrayList) with u32 indices. Tokens hold only a tag and a start offset; the lexeme is re-sliced from source on demand. AST node = tag + main_token + lhs/rhs u32, with variable-length payload moved to an `extra_data: Vec<u32>` side array. Booleans are stored out of band. Tagged encodings replace polymorphism. | numbers: Token 64 B -> 5 B. AST node 120 B -> 15.6 B average. ZIR instruction 54.0 B -> 20.3 B average. Parser: 22% faster wall time, 28% fewer instructions, 15% fewer cache misses. ZIR rework: 0.93 s -> 0.57 s (-39%) and peak memory 645 -> 386 MiB (-40%). AstGen over the whole std lib runs at 8.9M lines/s on an 8-core i9-9980HK (33 ms cold), which is about 1.1M lines/s per core if scaling were perfect (estimate). ZIR for os.zig is 472 KB against 630 KB of source+tokens+AST. | relevance_to_boon: Boon's `AstToken` (crates/boon_syntax/src/lib.rs:1863-1870) is { kind, lexeme: String, line, column, start, end: usize }. That is 57 B, padded to 64 B, which is exactly Zig's 'before' layout. It also carries a heap String per token, and the parser clones a second heap String per token into `ParserLine.symbols` (crates/boon_parser/src/lib.rs:5469). So Boon's front end sits at Zig's pre-DOD point plus two allocations per token. | source: https://ziglang.org/download/0.8.0/release-notes.html ; https://www.josherich.me/podcast/andrew-kelley-practical-data-oriented-design-dod ; https://mitchellh.com/zig/parser
- system: Carbon toolchain (Chandler Carruth; CppNow 2023, NDC Toronto 2026) | technique: Distinct lex, parse and check passes over dense homogeneous arrays with flyweight 32-bit IDs. The parse tree is a post-order array (`SmallVector<NodeImpl>` indexed by an int32 Parse::Node). Check is a single post-order pass with an RPN-style node stack. SemIR::Inst = kind + TypeId + up to two 32-bit operands. Types and constants are deduplicated to canonical TypeId/ConstantId values, so comparison is by id. The team wrote its own hash table and prefers weaker but faster hashes because hash latency dominates once probing is good. | numbers: Targets: lex+parse 10M lines/s (~100 ns/line), semantic analysis 1M lines/s (~1 us/line), lowering to binary 0.1M lines/s. The talk says 'we can't allocate memory per token'. The NDC 2026 summary reports those targets reached on Apple M4 for lexing and checking. Custom hash table: lookup hits ~23% faster than Abseil, insertion ~2x faster. | relevance_to_boon: Gives per-line budgets. Boon today on NovyWave (11,926 lines, measured): parse 5.4 us/line (~54x the Carbon lex+parse budget), typecheck 61 us/line (~61x the check budget), verified end-to-end 157 us/line (~16x the lowering budget). Both Carbon and Zig do type identity by interned id. Boon's kernel TypeTermArena does this too (crates/boon_compiler_kernel/src/term.rs:601-629), but the other phases do not. | source: https://lilys.ai/notes/1048442 (CppNow 2023 talk notes) ; https://daily.dev/posts/benchmarking-and-optimizing-the-carbon-compiler---chandler-carruth---ndc-toronto-2026-i4ljgsvpo ; https://docs.carbon-lang.dev/toolchain/docs/ ; https://docs.carbon-lang.dev/toolchain/docs/check/
- system: oxc parser (Rust) vs swc vs Biome | technique: All AST nodes live in a bumpalo arena with O(1) bulk free. Spans are u32. Identifiers use CompactStr (up to 24 B inline) or arena Atoms. Scope binding, symbol resolution and complex syntax errors are deferred to a separate semantic pass, so the parser does one job. Whitespace skipping uses SIMD. The benchmark binary is built with mimalloc, lto='fat' and codegen-units=1. | numbers: typescript.js (171,676 lines, 8,207,497 B; line and byte counts measured by me) parses in 26.3 ms on an M3 Max: 6.5M lines/s, 312 MB/s single-threaded. cal.com.tsx (30,591 lines, 1.06 MB) takes 3.4 ms: 9.0M lines/s. swc is 84.1 ms (2.0M lines/s) and Biome's CST is 130.1 ms (1.3M lines/s). Peak memory is 68.8 MB for the 8.2 MB file: 8.4x source bytes, ~0.4 KB per line. AST drop costs 0.3 ms for oxc vs 7 ms for swc. | relevance_to_boon: Boon's marginal parse rate, measured today as (TodoMVC minus counter), is ~6.9 MB/s (~245k lines/s). That is ~45x below oxc in bytes/s. Assuming the M3 is 1.5-2x faster single-threaded than this i7-9700K (estimate), the normalized gap is still ~25-30x. Boon peak RSS on TodoMVC verified is 153.8 MiB for 105 KB of package source, ~44 KB per line and ~110x oxc's per-line footprint. | source: https://github.com/oxc-project/bench-javascript-parser-written-in-rust ; https://oxc.rs/docs/learn/architecture/parser.html ; api.github.com file sizes plus streamed wc -l of the two input files
- system: Ruff (Astral) hand-written parser | technique: A hand-written recursive-descent parser replaced the LALRPOP-generated one. It is a structural change, not a micro-optimization. | numbers: Parser alone is 2.2-2.4x faster (large/dataset.py 63.6 -> 26.6 ms). End-to-end lint and format got 20-40% faster (e.g. CPython lint 134.6 -> 94.4 ms). | relevance_to_boon: Boon's parser is a line-oriented, string-matching, multi-pass design. parse_ast_traced (crates/boon_parser/src/lib.rs:4378-4460) runs, in order: lex, text-body line ranges, parser_lines, `lines.clone()` (4394), three merge_multiline passes, items, statement tree, three link/normalize passes and two validations. Then the index build, boundary validation, declared-function collection, item index and SHA-256 route digests run (2858-2887), followed by four policy validators (2784-2786 / 2804-2842). The measured result is 235,979 validation visits for 4,858 parsed expressions on TodoMVC (48.6 per expression) and 885,057 for 17,721 on NovyWave. Replacing the architecture is the lever; tuning individual passes is not. | source: https://astral.sh/blog/ruff-v0.4.0
- system: rust-analyzer / rowan (red-green CST) and Biome CST | technique: Lossless green trees with structural sharing (dedup through a NodeCache) and red cursors on top. This is optimized for incremental editing, not for batch throughput. | numbers: The rust-analyzer team's own plan (issue #17491) reports syntree, which has no structural sharing, builds trees 2x faster than rowan, and proposes a contiguous representation. The oxc benchmark shows Biome's CST parse 4.9x slower than oxc's AST parse. | relevance_to_boon: Do not adopt a red-green tree to get editor losslessness. Keep a flat token array (with trivia flags or ranges) next to a compact post-order AST. Get warm reuse from per-unit or per-owner fingerprints, not from a pointer-shared tree. | source: https://github.com/rust-lang/rust-analyzer/issues/17491 ; https://github.com/oxc-project/bench-javascript-parser-written-in-rust
- system: rustc memory model (arenas, interning, size asserts) | technique: Arena allocation tied to 'tcx. Ty<'tcx> and other types are interned so equality is pointer equality. Symbols are u32. rustc_ast carries static_assert_size! guards on hot node types (e.g. Attribute 32 B, Block 48 B, AssocItem 160 B). IndexVec and newtype_index give typed dense ids. DenseBitSet/ChunkedBitSet provide dense sets. | numbers: Shrinking Token from 32 to 24 B gave -0.5% to -0.7% on some benchmarks. Going from 24 to 16 B was 'negligible' and was abandoned (Nethercote). | relevance_to_boon: Caveat: shrinking structs that are already compact is second-order. The order-of-magnitude wins come from removing per-node heap allocation, pointer trees, string keys and redundant passes, which is where Boon is. In Boon only the kernel term arena has size asserts (crates/boon_compiler_kernel/src/term.rs:2903-2906: TypeTermHeader 24 B, ObjectFieldTerm 8 B). The parser, syntax, semantic and plan crates have none, and their node types embed String and Vec<String>. | source: https://rustc-dev-guide.rust-lang.org/memory.html ; https://doc.rust-lang.org/beta/nightly-rustc/rustc_ast/ast/index.html ; https://blog.mozilla.org/nnethercote/2018/06/05/how-to-speed-up-the-rust-compiler-some-more-in-2018/
- system: Hash functions in Rust compilers (FxHash / rustc-hash 2 / foldhash vs SipHash) | technique: Use a fast, low-quality, deterministic hasher for in-process tables whose keys are integers or ids. rustc uses FxHashMap everywhere. rustc-hash 2.0 (Orson Peters) swapped in a polynomial hash with a rotation finish plus a wyhash-style string compressor. | numbers: rustc: fnv -> fx gave up to 6% speedup. fx -> ahash was 1-4% slower. fx -> default SipHash was 4-84% slower. foldhash on a Xeon: u64 key 0.79 ns (foldhash-f) vs 0.67 ns (fx) vs 9.09 ns (SipHash); strings 2.63 vs 3.24 vs 11.87 ns. | relevance_to_boon: The 13 compiler crates contain zero uses of FxHash, foldhash, ahash or a custom BuildHasher (grep). Every HashMap uses std SipHash-1-3 with RandomState. Examples: `HashMap<u32, ...>` memo tables at crates/boon_compiler_kernel/src/solver.rs:373-386, `structural_widen_cache: HashMap<(TypeTermId, TypeTermId), TypeTermId>` at term.rs:617, and the resource maps at owner.rs:4858 and 5096-5101. The manual interners `HashMap<u64, Vec<KernelSummaryValueId>>` (owner.rs:18928, 19150) allocate a Vec per bucket where hashbrown::HashTable would store ids directly. | source: https://nnethercote.github.io/perf-book/hashing.html ; https://github.com/rust-lang/rustc-hash/pull/37 ; https://github.com/orlp/foldhash
- system: Cryptographic vs non-cryptographic digests (SHA-256 vs XXH3 / SipHash128), measured on this machine | technique: Use crypto digests only where an adversary or a cross-machine content-addressed store can turn a collision into a silently wrong artifact. rustc's incremental cache persists 128-bit query fingerprints across sessions and uses SipHash128 (StableHasher). It switched there from BLAKE2 for speed (PR #45319). | numbers: Measured on this i7-9700K, which has no SHA-NI, with `openssl speed -evp sha256`: 16 B messages 65.6 MB/s (~244 ns per digest), 32 B 131 MB/s (~244 ns), 64 B 174 MB/s (~368 ns), 16 KB 590 MB/s. The xxHash README, benchmarked on the same i7-9700K: XXH3 59.4 GB/s (AVX2) or 31.5 GB/s (SSE2), XXH64 19.4 GB/s. That is ~100x SHA-256 on bulk data. Small-key hashing with Fx or foldhash is ~1 ns vs ~244 ns for SHA-256. | relevance_to_boon: The compiler crates mention SHA-256 ~186 times. Hot in-process uses: (1) PlanRowExpressionArena::intern (crates/boon_plan/src/lib.rs:8985-9002) CBOR-encodes every candidate node into a fresh Vec (`binary::encode`, lib.rs:14554-14561), SHA-256s it, looks it up in a `BTreeMap<[u8;32], Vec<PlanRowExpressionId>>` (lib.rs:8869), and then still runs full structural equality. The collision resistance is paid for and never used. (2) The parser computes at least two SHA-256 route digests per expression plus per-statement digests, each path-length proportional, and inserts every digest into a BTreeMap<[u8;32], usize> collision check (crates/boon_parser/src/lib.rs:9380-9440, 9495-9545). At ~244-500 ns each that is ~11.6k digests on TodoMVC, roughly 3-6 ms of its ~14.5 ms marginal parse (estimate). (3) semantic_image.rs:2599-2640 and 3125-3150 run ciborium CBOR + SHA-256 on each projection intern miss. (4) receipt.rs:3153-3239 implements std::hash::Hasher by buffering every byte into a Vec and then SHA-256ing it. | source: openssl speed run on this host (i7-9700K, flags: avx2, bmi2, no sha_ni) ; https://github.com/Cyan4973/xxHash ; https://rustc-dev-guide.rust-lang.org/queries/incremental-compilation-in-detail.html ; https://github.com/rust-lang/rust/pull/45319
- system: PGO / LTO / BOLT / codegen-units on compiler binaries | technique: Profile-guided optimization trained on representative inputs, fat or thin LTO with codegen-units=1, and post-link BOLT layout. | numbers: rustc PGO on x86_64 Linux: up to 6% fewer instructions and up to 19% faster -j1 wall time (PR #88069); commonly cited as 'up to 15%'. LTO of librustc_driver: mean -4.1%, max -9.6% instructions. BOLT on LLVM: cycles mean -3.7%, max -6.6%. rust-analyzer PGO: analysis-stats ~20% faster. BOLT on Clang: +15.0% on top of LTO+PGO and +7.45% on top of GCC PGO; up to 20.4% on top of FDO+LTO and up to 52.1% without them. | relevance_to_boon: Boon's release profile is `lto = false`, `codegen-units = 16` (Cargo.toml [profile.release]) with target-cpu=generic. These are frozen in the measurement contract (budgets/compiler.toml:16-17: `target_cpu = "generic"`, `profile_options = "opt-level=3;lto=false;codegen-units=16;..."`) and attested by crates/boon_cli/build.rs:~110-116. Combined with the AGENTS.md rule 'Never edit budgets/compiler.toml', the protocol rules out a well-documented 10-25% combined build-level win (estimate from the rustc and rust-analyzer numbers) and measures a handicapped product binary. | source: https://github.com/rust-lang/rust/pull/88069 ; https://kobzol.github.io/rust/rustc/2022/10/27/speeding-rustc-without-changing-its-code.html ; https://github.com/rust-lang/rust-analyzer/pull/19582 ; https://arxiv.org/pdf/1807.06735
- system: Allocators (jemalloc / mimalloc vs system) | technique: Replace glibc malloc for allocation-heavy compilers. rustc, Sorbet and the oxc bench all do. | numbers: rustc shows an 8-10% compile-time regression without jemalloc (issue #36963). Sorbet links jemalloc. The oxc benchmark uses mimalloc. | relevance_to_boon: Already spent: boon_cli installs mimalloc as the global allocator on Linux (crates/boon_cli/src/main.rs:1-7; budgets/compiler.toml:11). The remaining allocation lever is structural: per-revision arenas, no String per token or node, and skipping teardown at process exit. The product sample reports allocation counters of 0 because the counting allocator runs only in the evidence lane, so allocation volume is invisible in normal samples. | source: https://github.com/rust-lang/rust/issues/36963 ; https://blog.nelhage.com/post/why-sorbet-is-fast/ ; https://github.com/oxc-project/bench-javascript-parser-written-in-rust
- system: Sorbet (Stripe Ruby typechecker) | technique: Names and symbols are interned to 32-bit NameRef/SymbolRef, so name comparison is one integer compare and never touches UTF-8. Symbols live in large flat arrays indexed by u32. It uses flat_hash_map and InlinedVector, builds error text lazily, and runs local-only, forward-only inference (one pass over each method's CFG, parallelizable). Built with LTO and jemalloc. | numbers: ~100,000 lines/s per core on Stripe's codebase. `sorbet -e 1` end to end in under 30 ms. | relevance_to_boon: Boon typecheck runs at 9.7k lines/s on TodoMVC (368.6 ms / 3,576 lines) and 26.4k lines/s on NovyWave, both measured: 4-10x below Sorbet single-core. The work counters show why. TodoMVC has 350 checked calls but 10,537 compiled call sites, 82,451 linked operations for 4,079 expressions, and 416,698 summary node evaluations: whole-program specialization per call path instead of local or once-per-definition inference. Boon also builds diagnostic strings eagerly on success paths (`diagnostic_path: format!(...)` at crates/boon_semantic/src/storage_contract.rs:927, 995, 1127, 1200). | source: https://blog.nelhage.com/post/why-sorbet-is-fast/
- system: TypeScript native port (tsgo) | technique: A port to Go (native code, shared-memory parallel checking) of a structural type checker. | numbers: VS Code, 1,505,000 LOC: 77.8 s -> 7.5 s, i.e. ~19k -> ~200k lines/s aggregate across threads. Playwright 356k LOC 11.1 -> 1.1 s. Memory roughly halved. | relevance_to_boon: A structural checker for a type-annotation-light language (TS inference is heavy) reaches ~200k lines/s multi-core. Boon's 10-26k lines/s sits at the level of the old JavaScript-hosted tsc. | source: https://devblogs.microsoft.com/typescript/typescript-native-port/
- system: TinyCC (whole-pipeline reference) | technique: Single-pass compile: parse, check and codegen in one sweep with no IR tree. | numbers: Links browser, 76,936 lines: 2.27 s = 859,000 lines/s on a 2.4 GHz Pentium 4 (2002), vs GCC 3.2 -O0 at 98,000 lines/s. Includes assembly and linking. | relevance_to_boon: Upper-bound reference for a lowering pipeline. Boon's verified pipeline runs at 4.5k lines/s (TodoMVC, 791 ms) and 6.4k lines/s (NovyWave, 1,875 ms) on hardware ~10x faster than a P4 (estimate). | source: https://bellard.org/tcc/
- system: Hash-consing (Filliâtre & Conchon, ML 2006) | technique: Maximal sharing gives each term a unique integer tag, making equality and hashing O(1) and enabling id-keyed tables. | numbers: Memory reduced by more than 3x in case studies. Term creation can be ~2x slower in adversarial cases. Operations that compare or reuse terms get orders of magnitude faster. | relevance_to_boon: Hash-cons values that are compared and reused (types, summaries, row expressions). Do not hash-cons one-shot AST nodes. Boon's kernel TypeTermArena does this correctly with SoA rows (term.rs:601-629). But boon_checked::Type (crates/boon_checked/src/lib.rs:35-71) is still a tree with derived deep Hash and Eq, and its ObjectShape { fields: BTreeMap<String, Type>, field_order: Vec<String> } (lib.rs:311-316) stores every field name twice as an owned String. Semantic IR goes back to owned Strings (crates/boon_semantic/src/execution.rs:506-596: path: String, projection: Vec<String>, canonical_path: String, Tag(String), name/function: String). The kernel is a DOD island whose interning is undone at the kernel-to-semantic boundary. | source: https://usr.lmf.cnrs.fr/~jcf/publis/hash-consing2.pdf
- system: Dense-id containers: IndexVec, bitsets, CSR adjacency | technique: When ids are dense u32s assigned in a deterministic order: map id -> value with IndexVec<Id, T>, represent sets with a DenseBitSet (plus popcnt), and store graphs as CSR (offsets: Vec<u32>, targets: Vec<u32>) built once. Replace visited sets with epoch-stamped Vec<u32> arrays. Determinism follows from id order, so ordered maps are unnecessary. | numbers: No single published number. These are textbook techniques that rustc_index and every DOD compiler use. Repo evidence (a samply profile recorded by the owner's earlier session, not reproduced by me because samply needs perf_event_paranoid <= 1 and I may not change that security setting): in TodoMVC diagnostics a BTreeSet path set took ~11%, `direct_result_summary_supported` 36.3% inclusive, and `schedule_variable` 15.8% self, the last walking `Vec<Vec<TypeVariableId>>` adjacency. | relevance_to_boon: The compiler crates mention BTreeMap ~3,300 times and BTreeSet ~1,800 times (boon_semantic 506/538, boon_compiler 515/326, boon_typecheck 1,020/600, much of it cfg-gated legacy). boon_semantic has 43 BTreeSet<SemanticExprId> and 22 BTreeMap<DeclId, ...> keyed by dense ids. boon_compiler has 47 BTreeMap<String, ...>. The kernel solver's binding_dependencies and binding_dependents are Vec<Vec<TypeVariableId>> (crates/boon_compiler_kernel/src/solver.rs:302-303). The pattern looks like the byte-identical-output requirement being met with ordered containers instead of deterministic id assignment. | source: https://doc.rust-lang.org/beta/nightly-rustc/rustc_index/ ; docs/plans/evidence/compiler-profile-driven-t0-2026-09-28.json (repo claim)
- system: Boon parser line/column tracking and fixed overhead (measured) | technique: Anti-pattern: after scanning each token, the lexer re-decodes its characters to compute line and column eagerly, and bumps a work counter per character. DOD compilers store only a u32 start offset and compute line/column lazily from a line-start table when a diagnostic is rendered. | numbers: Measured `source_bytes_inspected` is exactly 2x the parsed bytes: TodoMVC 206,254 = 2 x 103,127 (package bytes minus BUILD.bn), NovyWave 866,742 = 2 x 433,371. token_inspections is 304,851 on TodoMVC (~3 per source byte), estimated at ~15-18 inspections per token. counter.bn (3,352 B) spends 3.6 ms in the parse timer across 5 repeats, i.e. 0.9 MB/s. That is almost all fixed per-compile cost inside the parse timer, since the marginal rate is ~6.9 MB/s. | relevance_to_boon: advance_lexer_position (crates/boon_parser/src/lib.rs:5405-5420) is the second pass. `lexeme: lexeme.to_owned()` (5393) is the per-token allocation. For the warm edit budget (16.7 ms), re-parsing TodoMVC's RUN.bn (34,661 B) costs ~5 ms at the marginal rate, plus some share of the ~3.5 ms fixed cost. That is 30-50% of the whole warm budget before any checking (estimate). The parser has to get ~10x faster, or incremental, for the warm budget to be reachable at all. | source: compiler-sample runs on target/release/boon_cli today (JSON in the scratchpad dod/ folder) ; crates/boon_parser/src/lib.rs

## recommendations_for_boon
- Rebuild the front end as one DOD pass instead of optimizing the current 15+ pass line/String parser. Tokens become SoA {kind: u8, start: u32}, with the lexeme sliced from source. Line and column come lazily from a `line_starts: Vec<u32>` binary search, only when a diagnostic is rendered; delete advance_lexer_position (boon_parser/src/lib.rs:5405-5420). Indentation becomes INDENT/DEDENT tokens (Python/ruff style) instead of ParserLine/ParserItem merging. Produce a post-order node array {tag: u8, main_token: u32, lhs: u32, rhs: u32} plus `extra: Vec<u32>`, with ids born final so no pack/rebase passes are needed (lib.rs:1138, 3361). Fold the validation index and the four policy validators into that one post-order walk. Target >= 2M lines/s, which is what makes the 16.7 ms warm budget reachable: reparsing RUN.bn currently costs ~5 ms at the marginal rate.
- Intern once, at the lexer, and never de-intern. Promote the kernel's ProjectTextSnapshot/symbol ids to the lexer. Replace String and Vec<String> in AstExprKind (boon_syntax/src/lib.rs:1667+), AstStatementKind, boon_checked::ObjectShape (fields: BTreeMap<String, Type> plus a duplicate field_order: Vec<String>, boon_checked/src/lib.rs:311-316), SemanticExpressionKind (boon_semantic/src/execution.rs:506-596) and plan tables with Symbol(u32) / PathId(u32) into a path table. Strings should appear only in diagnostic rendering and final artifact serialization. Delete the dotted-path join/split traffic (38 join(".") and 12 split('.') in boon_semantic, e.g. memory_contract.rs:717-722).
- Get SHA-256 off the in-process path. Identity and interning should use foldhash or rustc-hash 2 over the node's fields, a hashbrown::HashTable of ids, and structural equality on collision. Never serialize to CBOR to obtain a hash key (boon_plan/src/lib.rs:8985-9002 + 14554-14561; boon_semantic/src/semantic_image.rs:2599-2640). Cross-edit or cross-process fingerprints should be 128-bit non-crypto (XXH3-128 or SipHash128, as rustc incremental does), composed bottom-up during construction. Keep SHA-256 only for the single artifact seal that crosses a trust or persistence boundary, computed once over canonical bytes. On this CPU (no SHA-NI) each small SHA-256 costs ~244-368 ns, against ~1 ns for Fx.
- Make FxHashMap/FxHashSet (rustc-hash 2) the workspace default in compiler crates and add a clippy `disallowed-types` rule for std::collections::HashMap/HashSet (and for BTreeMap/BTreeSet outside an allowlisted output-boundary module). rustc measured 4-84% slowdowns from SipHash. Boon has zero non-SipHash tables today.
- Replace ordered containers keyed by dense ids with IndexVec<Id, T> or IndexVec<Id, Option<T>>, replace sets with DenseBitSet, or with sorted Vec/SmallVec when sparse, and use epoch-stamped visited arrays instead of per-walk BTreeSet/HashSet. Get determinism by assigning ids in source order and sorting only at the artifact boundary. Start with boon_semantic's 43 BTreeSet<SemanticExprId> and 22 BTreeMap<DeclId, ...>, and boon_compiler's 47 BTreeMap<String, ...>. The owner's own profile already caught one BTreeSet path set at ~11% of TodoMVC diagnostics.
- Build graphs once as CSR (offsets + targets, u32) per program: kernel binding_dependents/dependencies (solver.rs:302-303, today Vec<Vec<TypeVariableId>>), consumers, dependency manifests. Walk them with bitsets or epoch stamps.
- Use per-revision arenas (Vec-backed typed stores or bumpalo) for AST, checked, semantic and plan data. In fresh-process mode, skip teardown (mem::forget or exit) as oxc's numbers suggest (0.3 ms vs 7 ms drop). Budget memory at <= 2 KB/line; this alone would fix the currently violated peak_rss budgets (TodoMVC 153.8 MiB vs 128, counter 39.3 vs 32).
- Add assert_eq_size! guards (static_assertions is already a workspace dependency) to every hot node type: token <= 8 B, AST node <= 16 B plus extra, IR/semantic instruction <= 16-24 B (Carbon-style kind + type + 2 operands). Today only the kernel term arena has them (term.rs:2903-2906).
- Open a product-optimized build lane and put it in front of the owner. Today budgets/compiler.toml:16-17 and boon_cli/build.rs freeze target_cpu=generic, lto=false and codegen-units=16, and AGENTS.md forbids editing budgets/compiler.toml. Evaluate lto='fat' + codegen-units=1 + target-cpu=x86-64-v3, then PGO trained on counter/TodoMVC/NovyWave via cargo-pgo, then BOLT. Published gains: PGO 15-20%, LTO 4-10%, BOLT 2-15%. Keep the determinism oracle (plan_sha256 equality), because build flags do not change output bytes. Measuring a deliberately handicapped binary is a process decision; it is not a requirement of the language or the product.
- Report per-phase throughput (lines/s, bytes/s, bytes/line of memory) in compiler-sample next to ms per fixture, and set CI targets from the table: parse >= 2M lines/s, check >= 100k lines/s, back half >= 50-100k lines/s. Fixture-ms budgets hide where the per-line cost lives. The counter's 3.6 ms parse of 3.35 KB, i.e. fixed overhead, would stand out immediately.
- Construct diagnostics lazily (Sorbet): no `diagnostic_path: format!(...)` on success paths (boon_semantic/src/storage_contract.rs:927, 995, 1127, 1200). Store (kind, ids, span) and render text only when a diagnostic is emitted.
- Do not adopt rowan or red-green trees for the compiler. rust-analyzer's own team measures a contiguous tree building 2x faster, and Biome's CST parses 5x slower than oxc's AST. If the editor needs losslessness, keep trivia in the flat token array.
- Critique of the active plan (BOON_COMPILER_PROFILE_DRIVEN_PLAN_2026_09_28.md): its profile-first discipline is right, but in the data-model dimension it is incremental. T2 and T4.4 treat hashing and interning as 'a few percent each'. It says nothing about the parser's architecture (two heap Strings per token, bytes scanned twice, ~49 validation visits per expression), the de-interning boundary between the kernel and the semantic IR, or pervasive BTree and SipHash use as one systemic issue. T6, the algorithmic change that is the only credible route to Sorbet-class checking (10,537 compiled call sites from 350 checked calls on TodoMVC), is marked 'research, not scheduled'. Recommend scheduling T6 in parallel with a DOD data-model rewrite (items 1-5) rather than after T1-T5.
- Raise with the owner: budgets/compiler.toml:22 `compiler_threads = 1` rules out per-unit parallel parse and check. Zig's 8.9M lines/s AstGen and tsgo's 10x both lean on parallelism. Keep single-thread performance as the primary target (rust-analyzer's plan: fix single-core first), but do not forbid parallel per-unit work in the product.
- Re-profile before each step. samply needs perf_event_paranoid <= 1, and I did not change that (it is a kernel security setting), so every hot-spot percentage in this report that comes from the repo's T0 evidence is a claim I did not reproduce.

- crates/boon_syntax/src/lib.rs:1863-1870 - AstToken { kind, lexeme: String, line: usize, column: usize, start: usize, end: usize }: 64 B plus one heap allocation per token (Zig: 5 B, none).

- crates/boon_parser/src/lib.rs:5405-5420 - advance_lexer_position re-decodes every token's chars to compute line/column eagerly. Measured source_bytes_inspected is exactly 2x source bytes (TodoMVC 206,254 = 2 x 103,127; NovyWave 866,742 = 2 x 433,371).
