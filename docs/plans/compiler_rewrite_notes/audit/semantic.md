## key
semantic
## subsystem
boon_semantic: elaboration from the checked/kernel program to CanonicalProgramCoreV2. Covers contextual expansion, the resource/reactive/storage/lowering/view/memory graphs, execution receipts, the dependency manifest, the semantic image and digests.
## purpose_summary
Entry point: boon_semantic::elaborate_kernel_runtime_packed → elaborate_with_representation (crates/boon_semantic/src/lib.rs:2781, 2833-3380). It is timed as semantic_ms in boon_compiler/src/lib.rs:79-107. The production path takes both the rich CheckedProgramFields rows and the packed KernelSemanticInputV1, and runs 24 traced phases. (1) Input validation, plus CallCatalog and CallTypeCatalog, which turn kernel type terms back into boxed boon_checked::Type trees. (2) verified_intent: demand roots and 'ordinary' retained definitions (312 of 497 on NovyWave). (3) out_net: a tree of call instances with parent pointers, built per call path, with ports, nets and a static-owner forest. It makes 3494 instances from 1821 checked call sites and expands 1317 frames. (4) contextual materializations and derive_semantic_execution_graph: each checked expression is expanded once per (expression, frame, value_frame, owner) into SemanticExecutionImageColumnsV1, giving 16340 expressions. (5) Six side graphs are built from it: resource, reactive, lowering contract, scope storage, view binding and memory. Each gets its own ID space, and most get a CBOR+SHA-256 digest plus 'dependency rows'. (6) core_lowering maps everything into CanonicalProgramCoreV2. That is a 1:1 renamed copy of the execution image plus remapped side tables, with executable ids required to equal semantic ids (core_lowering.rs:1589-1601). During that mapping, ExecutionReceiptPublisherV5 SHA-256-seals every scope, expression, statement, call and owner row. (7) build_callable_dependency_manifest_v7 builds a proof manifest and a SealedRequestGraphSnapshot. (8) The semantic image is sealed and the program digested. Downstream, only canonical_core leaves the crate through into_lowering_parts (lib.rs:1068-1082), plus digests. boon_verify reads only dependency_manifest.manifest_digest and the schema digest, and reactive_graph.pulse_batches for pulse-fusion decisions (boon_verify/src/lib.rs:878-925). boon_ir wraps the core and re-validates it. The request graph is stored in session state and read only by a test (session.rs:804-809, 1440-1465). semantic_program_digest and verification_manifest_digest are copied into CompiledSealedMachinePlanFromSource (boon_compiler/src/lib.rs:519-534), and nothing reads them there. The only semantic digest that reaches the plan is the per-pulse-batch semantic_slice_digest (boon_plan/src/lib.rs:5720; the plan checks only that it is non-zero, :13216). I measured the split with a gdb-based stack sampler; samply was blocked because perf_event_paranoid=2 and I did not change system settings. Result: 56.8% of NovyWave semantic samples (n=972) and 50.3% of TodoMVC samples (n=429) are receipts, digests, manifest or validation. Leaf SHA-256 alone is 29% and ciborium CBOR 10%. Trace timers give about 415 of 794 ms (NovyWave) and 81 of 161 ms (TodoMVC). None of that affects the plan.
## essential_work
- Demand/reachability from program roots (render output, SOURCEs, HOLD/state, lists, consequential effects), so dead declarations are not lowered. Today this is verified_intent, 10.2 ms on NovyWave, and is essentially linear.
- Deciding instance identity for stateful code. HOLD/LATEST/SOURCE/LINK inside a function called from N places, or inside a LIST row body, needs a distinct state/source identity per call path or row owner. That requires a static-owner forest (546 owners on NovyWave, 23 on TodoMVC) and a call-instance tree for stateful or context-dependent functions only.
- One concrete runtime type per runtime node, for storage layout and plan types. The kernel already solves per-call-path types, so elaboration should only reference them, not re-derive them.
- Lowering each typed expression form (records, tags, pipes, WHEN/WHILE/THEN, LATEST, HOLD, LIST ops, text, calls, FLUSH) to a dataflow IR node with explicit children, once per template or instance.
- Value-origin analysis: which state, source or row-local a value comes from. It drives storage decisions and row-local reads. Today this is per-expression provenance vectors.
- Reactive schedule: for each SOURCE/trigger, the set of affected nodes in topological order (pulse batches), state update arms, list mutations, derived values, dependency edges and host-effect schedules.
- Storage allocation: slots for state cells, lists, row fields, locals, bindings and captures per static owner (scope_index).
- View/render bindings and output root values; source payload schemas; host port declarations.
- Persistence identity for HOLD/LIST (semantic_memory, migration_edges), so schema migrations can match state across program versions.
- Diagnostics for programs that pass type checking but cannot be elaborated (recursive contextual calls, expression cycles, unbound outputs).
- Optionally, static folding of WHEN/WHILE arms whose selector is statically known across all call sites. It changes demand and therefore which state exists, so it is semantic-adjacent and must be done once, correctly, and with an index.

## from_scratch_design
Three representations, four passes, no self-proofs in the product path.

R0, typed HIR (checker output, kept as is). An arena of nodes with u32 NodeId. Each node has an op (u8), a TypeId (u32) into the checker's hash-consed type-term arena (the kernel already has TypeTermArena, so never export boxed boon_checked::Type), a children range into a flat u32 array, and a resolved DefId/SymbolId. Per call site, the kernel exports the callee DefId and a TypeId slice of type arguments, or directly the solved TypeId of every node per invocation frame. The kernel already enumerates invocation frames (703), so it should export the frame tree once instead of semantic rebuilding it.

P1, demand plus instantiation plan: one worklist from the roots over the call graph. Classify each reachable function once:
- Pure template: no HOLD/SOURCE/LINK/host effect, no ambient context. Compiled once per (DefId, type-arg tuple), memoized in an FxHashMap, and called by reference at runtime or inlined by the backend.
- Stateful or contextual component: instantiated per call path. Build an instance tree Vec<Instance{template, parent: u32, call_site: NodeId}> and the static-owner forest for LIST row regions. Record the param→actual-argument index here. That index makes static WHEN/WHILE selector folding O(1) per query and replaces both evaluators (out_net.rs:1924 and contextual_expansion.rs:9030).

P2, lower HIR→RIR (reactive IR), per template/instance: one recursive visit memoized in a Vec<u32> indexed by HIR NodeId within the template (no BTreeMap ExpansionKey). Each RIR node is a plain struct {op: u8, flags: u8, ty: TypeId u32, a: u32, b: u32, args: u32 start, u16 len}, about 16-20 bytes. Ops: Const, Field, Record, Tag, Call(template), Latest, Hold(state slot), Then/When/While (event-gated), Source(port), ListOp with a nested row region, Text, Render, Flush. Value-origin (provenance) is one u32 per node pointing at the origin node, not a Vec of string paths. Names are interned SymbolIds.

P3, analyses over RIR, all linear:
(a) Topological rank plus per-node trigger set as a bitset over sources (117 sources on NovyWave is 2 words per node) or an SCC id. This yields pulse batches, state update arms, list mutations and derived values.
(b) Storage slot allocation per static owner (state cells, lists, row fields, locals, captures).
(c) View bindings and output roots.
(d) Persistence identity per HOLD/LIST as (owner path, symbol) for migrations.
These are the six side graphs of today, but as side tables keyed by RIR node or slot ids, never as separately sealed graphs with their own ID spaces and remapping.

P4, emit: the backend consumes RIR plus side tables directly and emits the machine plan. CanonicalProgramCoreV2, ErasedProgram and the six graphs disappear. The only cryptographic hash is one over the final plan bytes, if an artifact cache or sharing needs it. semantic_slice_digest becomes a cheap structural hash, or the plan check is relaxed. Per-template content hashes, over HIR ops, TypeIds and callee hashes, are the natural warm-reuse key if one is ever needed. At the target speed it is not needed: full re-elaboration costs less than the 16.7 ms warm budget.

Correctness: debug_assert structural validators plus differential and fuzz tests run in CI, not on every compile. Diagnostics are data (enum plus spans); no format! on success paths.

Representation count: R0 (HIR, shared with the checker), R1 (RIR plus side tables), R2 (plan). Today's chain is CheckedProgramFields + CheckedImageHandoffV4 + KernelSemanticInputV1 + CheckedRuntimeFlowTermHandoffV1 → CallCatalog/CallTypeCatalog → VerifiedSemanticIntent → OutNet → materializations → ExecutionConstructionRoutesV3 → SemanticExecutionImageColumnsV1 → ExecutionConstructionImageV5 → Resource/Reactive/Lowering/Storage/View/Memory graphs → CanonicalProgramCoreV2 → ExecutionImageHandoffV5 → ManifestPrefixV7 → DependencyManifestV7 + RequestGraph → SealedSemanticImageV5 → ErasedProgram → MachinePlan. That is at least 20 structures.

On contextual expansion: today it is a second per-call-path instantiation. The kernel specializes per call path (compiled_call_sites 2699, invocation_frames 703, specialization_plans 584 + 2115 reused, max_call_depth 22). out_net then rebuilds its own instance tree (3494 instances, 1317 frames) by re-walking definition templates (reachable_calls, out_net.rs:1503-1600). It re-derives concrete types per frame by composing CheckedTypeSubstitution chains over boxed types, and runs its own static-selector evaluation. Expression growth is small (16340 semantic vs 15650 checked, because 312 'ordinary' definitions are shared). The cost is in the rebuilt call tree, per-frame type recomposition and the heavyweight per-node representation, not in node explosion. It also expands 185 'body_not_closed' functions per call path only because they read ambient context. Passing context as an ordinary parameter would make them templates. The single-instantiation design above has the kernel own the frame tree and P1 only mark which frames need state identity.
## speed_ceiling
Today's throughput: NovyWave semantic runs about 794 ms over 15,650 checked / 16,340 semantic expressions, roughly 50 µs per node. TodoMVC runs 161 ms over 4,081 / 4,536, roughly 36 µs per node. Counter pays about 8.4 ms, of which 4.9 ms is receipts and manifest.

Clean design, estimates:
- P1 is one worklist over about 2-3.5k call edges: under 0.5 ms.
- P2 lowers about 16-30k RIR nodes (including stateful instance duplication) at about 100-200 ns each with arenas and u32 ids: 2-6 ms NovyWave, 0.5-1.5 ms TodoMVC.
- P3 is 3-4 linear passes with bitset trigger sets (2 words per node on NovyWave) at about 50-100 ns per node per pass: 2-5 ms NovyWave, under 1.5 ms TodoMVC.
- No hashing except an optional single plan hash of about 13 MB at over 1 GB/s with xxh3: under 10 ms, and it can be skipped in preview.

Ceiling: about 5-15 ms for NovyWave semantic (50-150x faster) and about 1.5-4 ms for TodoMVC (40-100x). Even at a pessimistic 1 µs per node it is 16-35 ms NovyWave and about 5 ms TodoMVC. At that point full re-elaboration fits the 100 ms warm-preview budget without any incremental request graph.

Intermediate ceiling with the current architecture, only deleting proof work: NovyWave about 794 → 340-380 ms and TodoMVC about 161 → 75-80 ms, matching the 57% / 50% sampled shares. Fixing the listed O(n²) scans and type re-specialization adds roughly 60-100 ms NovyWave and 25-30 ms TodoMVC. Even then TodoMVC semantic alone (~50 ms) takes half of the 100 ms warm-preview budget. That is why the plan's T4 'preview mode' (estimated 783 → 420 ms) is too incremental. It keeps the representation and the second instantiation that cost the remaining 40x.

## representation_critique
- structure: boon_checked::Type (a boxed tree with BTreeMap<String, Type> object fields and Arc sharing) as the per-node type in every semantic and core struct | critique: Each of the 16k expressions owns a FlowType clone, twice (semantic and executable). Equality, ordering and closedness checks walk whole trees; unions are sorted by Debug string; specialization re-walks subtrees at every level. Sampled Type clone, drop, eq and BTreeMap<String,Type> operations are about 5-8% of semantic before counting specialization. | evidence: execution.rs:125, program_core.rs:693; boon_checked/src/lib.rs:35-72, 3872-3891, 4003-4012. | better: A u32 TypeId into the kernel's hash-consed term arena, with cached flags (closed, has_vars, renderable) and O(1) equality.
- structure: More than 19 intermediate structures inside one phase, each with its own ID space, mapping structs and bijection validation | critique: Each graph (resource, reactive, lowering, storage, view, memory) is built, digested, row-published and then translated into CanonicalProgramCoreV2. The information is side tables of one dataflow graph. | evidence: lib.rs:3195-3290; core_lowering.rs:7265-7560; architecture.rs:1994-1999 requires the map types. | better: One RIR node arena plus side tables keyed by node or slot id, produced in 3-4 linear passes.
- structure: BTreeMap/BTreeSet as the default container, typed usize ids re-validated on every lookup | critique: 1,044 BTree mentions vs 24 HashMap in the crate; 370 lookups of the form `.get(i).filter(|c| c.id == id)`. Memo keys such as ExpansionKey (4 fields) and BTreeSet<(SemanticExprId, Vec<String>)> allocate and compare deeply. | evidence: grep counts; contextual_expansion.rs:5784-5790, 6920-6950, 9030-9040. | better: u32 index newtypes into dense Vecs, trusted after construction. FxHashMap only for sparse keys; interned projection ids instead of Vec<String>.
- structure: Strings as per-node payload: resource_binding_path, provenance paths, projection field vectors, 2,220 format! sites | critique: Strings built and cloned for every expression are read almost only in error messages (boon_ir/src/lib.rs:3061-3068). Validators format context strings eagerly on success (execution.rs:1691). | evidence: execution.rs:133-136; program_core.rs:698-705, 737-742. | better: Interned SymbolIds and lazily rendered diagnostics.
- structure: SHA-256 over serde-CBOR as the identity and equality primitive (canonical_serde_hash_v1_with_buffer) | critique: Serializes struct field names and nested types through ciborium for every row, then SHA-256. It makes up 38-39% of semantic samples (leaf sha 29% plus cbor 10%). Cryptographic strength is unnecessary for in-process identity. | evidence: boon_contract/src/lib.rs:152-170; semantic_image.rs:2599-2700. | better: No per-row hashing. At most one fast hash of final plan bytes, and per-template content hashes over fixed binary layouts if caching needs them.
- structure: Dual input: rich CheckedProgramFields rows plus packed KernelSemanticInputV1, both consumed in the 'RuntimePacked' path | critique: Semantic still indexes program.expressions and scopes from rich rows (out_net.rs:1585-1590, lib.rs:3414) while also materializing types from kernel terms. This doubles input memory and splits authority between two representations. | evidence: lib.rs:2773-2778 ('transitional base rows'); call_view.rs, checked_view.rs rich/packed views. | better: A single typed HIR, R0, owned by the checker.
