## subsystem
Front end: source loading (boon_compiler compiler_source_project_for_path + boon_example_manifest), boon_parser (lex, line merging, items, AST, validation, identity digests, linking), boon_syntax DTOs, boon_contract source-bundle digest/text catalog, session reparse path (boon_compiler/src/session.rs)
## purpose_summary
The "parse" phase in compiler-sample is much more than parsing. It starts in boon_compiler/src/lib.rs:1731 compiler_source_project_for_path. That function reads examples/manifest.toml and fully validates it through ExampleManifest::from_path (boon_compiler lib.rs:1899, boon_example_manifest lib.rs:483). Validation canonicalizes about 200 referenced files and even reads unrelated migration .toml/.scn files. The function then canonicalizes every unit against a build-time CARGO_MANIFEST_DIR root to derive logical paths and reads the files. boon_parser then builds CanonicalSourceBundleV1, a SHA-256 over all source (lib.rs:2695). Each unit is lexed into Vec<AstToken>, one heap String per token. Tokens are regrouped into physical ParserLines (lexemes cloned again, lines.clone() at lib.rs:4394). Three line-merge passes follow (BYTES, DRAIN, multi-line call). Lines are classified into ParserItems (another set of Option<String> fields). A recursive statement tree is built from indentation. Each item's Vec<String> token slice is parsed by a cascade of whole-slice scans (ast_expr_kind, lib.rs:5961), with spans recovered by string-window search (span_for_tokens, lib.rs:5945). Four post-hoc repair passes fix the structure (arrow contexts, multiline pipeline linking, materialize, unary negation). Then comes a ValidationIndex plus about 10 policy validators that re-scan tokens and items with string compares, some of them path-keyed ("/examples/" at lib.rs:7509). Next, SHA-256 identity digests are computed for every statement, every expression, every call/pipe occurrence and every call site (CBOR+SHA). The unit is then linked by rewriting module strings and repacking every id in place (Arc::make_mut). Finally the ProjectSyntaxSnapshot is assembled, which hashes the whole bundle a second time (lib.rs:1558). Measured on NovyWave (433 KB, 73.6k tokens, 17.7k expressions) the phase takes 65 ms: lexing is about 3.3 ms and the whole AST build about 19 ms. Roughly 70% of the phase is incidental: manifest about 4%, validation about 14%, identity digests about 38%, snapshot and bundle digests about 7.5% (gdb-sampled shares). counter's 3.6 ms parse is 76% manifest loading (0.85 ms without it, measured). In the warm session the edited unit is reparsed whole. Unchanged units are reused after SHA-256 fingerprinting all sources (session.rs:852), but the snapshot and bundle digest are rebuilt over the whole project on every request. On TodoMVC a one-character edit costs 6.2-8.5 ms of parse, which is 37-51% of the 16.7 ms warm budget.
## essential_work
- Read each source unit once (8 files, <0.5 MB total), with project membership from a small per-project declaration, not a global fixture registry
- One lexing pass over the bytes (including a mode switch for TEXT { ... } bodies and {interpolation}), producing token kinds plus byte offsets
- Parse the brace/bracket, newline-sensitive grammar (records, LIST/MAP/SET, FUNCTION, pipes |>, WHEN/WHILE/THEN/HOLD/LATEST/BLOCK, continuation lines, `name:` NEWLINE INDENT value) into a tree, with exact spans and error recovery
- Report syntax errors, including removed or planned-feature spellings, while parsing
- Intern identifiers so later phases compare u32s rather than strings
- Build per-unit item index and declared-function list (module/function names)
- Assign stable identities to items (and, lazily, to sub-item nodes) usable as cross-revision reuse keys
- Compute one source-bundle digest where an artifact contract actually requires it
- Incrementally: reparse only the changed unit (or item) and keep unchanged units' results by identity, with no re-hashing

## from_scratch_design
Target: a front end in the oxc / Zig AST / Carbon style, not a lossless CST.

1. **Source database.** `SourceDb { units: Vec<Unit { path: Symbol, text: Arc<str>, rev: u64 }> }`. Project membership comes from a per-project declaration (BUILD.bn or a small package file) or a directory convention. It is resolved once per session with lexical path normalization only: no canonicalize loops, no dependency on CARGO_MANIFEST_DIR, and never the examples registry (that moves to xtask). Text is stored once and shared by Arc. A session edit bumps `rev` for one unit, so nothing is rehashed to discover what changed.

2. **Lexer.** One pass over the bytes with a 256-entry byte-class table. Output is SoA: `kind: Vec<u8>`, `start: Vec<u32>` (the end comes from the next start or a small `len: Vec<u16>`), plus per-line `indent: Vec<u16>` and a LINE_START flag bit in `kind`. Keywords (FUNCTION, LIST, HOLD, THEN, WHEN, WHILE, LATEST, BLOCK, TEXT, SOURCE, SKIP, FLUSH, ...) are matched by length+bytes to a TokenKind. `TEXT {` switches the lexer into raw-text mode with `{expr}` interpolation, so text spans are never reconstructed afterwards. Identifiers and paths like `List/map` are interned into a session-global `Interner` (hashbrown + FxHash, Symbol(u32), arena of bytes). Removed spellings (EXAMPLE, LINK, `#`) produce error tokens directly. Comments stay in the token stream for the editor and formatter. Expected speed: 300-1000 MB/s.

3. **Parser.** Hand-written recursive descent, with Pratt parsing for infix, `|>`, `=>` and `.field`, consuming token indices.
- Newline handling: a newline ends an expression except inside ()[]{} or when the next line starts with `|>` or an infix operator. `name:` NEWLINE INDENT expr parses the value from the next, more-indented line. This single rule replaces lines, items, line merging and all four repair passes.
- WHEN/WHILE arms and MAP entries parse `pattern => expr` according to the enclosing construct, so there is no Arrow intermediate or later consume_arrow_* pass.
- Output is a flat arena: `nodes: Vec<Node { kind: u8, flags: u8, a: u32, b: u32 }>` (12 bytes), `span_start: Vec<u32>`, `span_end: Vec<u32>`, and `extra: Vec<u32>` for variable-arity children (call args as [name Symbol, value NodeId] pairs, record fields, list items).
- Field access, call, pipe-call, WHEN, THEN, HOLD, LATEST and so on are distinct node kinds. Operators are enums, not `op: String` / "Field/x" strings. Statements are nodes too; there are no recursive Vec children.
- Ids are local u32. The global id is (unit u16, local u32) and is never rewritten.
- Errors recover at a newline or matching bracket and carry exact token spans.
- Expected speed: 50-150 MB/s including tree building.

4. **Identity, computed in the same pass.** An item's identity is the FxHash/xxh3-128 of (module Symbol, item-kind, name Symbols, same-name sibling ordinal). A node's identity is the rolling hash of (parent identity, child role, label Symbol, reverse sibling ordinal), stored as u64/u128 per node, or computed lazily only for nodes the typechecker keys on. There are no stored routes, no per-node SHA-256 and no collision BTreeMaps (use a debug_assert).

5. **Unit artifact.** It holds the token SoA, the node arena, the item table (name Symbol, kind, node range, identity), declared functions, and a per-unit content hash (xxh3). The item table is also the incremental reparse index. Top-level items start at column 0, so an edit maps to one item via a line-to-item table: relex and reparse that item only and splice its node range, falling back to reparsing the whole unit at 50+ MB/s (<1 ms for 35 KB).

6. **Project snapshot.** A persistent `Vec<Arc<UnitArtifact>>` plus a module-to-function map, patched per changed unit. The source-bundle digest is computed lazily at artifact export, with BLAKE3 or a single SHA-256.

7. **Parallelism.** Units are independent, so lex and parse them with rayon when the input exceeds about 100 KB. NovyWave has two ~200 KB units.

8. **Downstream contract.** Typecheck consumes Symbols and enum kinds. The editor gets token kinds and spans. If a serde JSON AST is still wanted for tooling, it becomes a debug projection and stops being the in-memory representation.
## speed_ceiling
All figures are estimates for the clean design, single core, on this i7-9700K.

**Assumptions.** Lexer ~5-10 ns/token. Tree building ~20-40 ns/node (nodes ≈ 0.5-0.6 per token). Interning ~15 ns per identifier. Item identity ~50 ns per item. One file read per unit.

- **NovyWave** (433 KB, 73.6k tokens, ~40k nodes, 6.9k items): lex 0.4-0.7 ms, parse 1-2 ms, interning 0.5 ms, identities 0.3-0.5 ms, file IO 0.1 ms, lazy bundle digest 0.2-1 ms. Total about 3-5 ms, versus 65 ms today (13-20x). About 2-3 ms with 2-4 threads, since NovyView.bn (188 KB) and RUN.bn (208 KB) dominate.
- **TodoMVC** (103 KB, 19.2k tokens): about 0.8-1.5 ms, versus 18 ms today.
- **counter** (3.4 KB, 718 tokens): about 0.03-0.1 ms, versus 3.6 ms today; 2.7 ms of that is the manifest.
- **Warm edit in TodoMVC RUN.bn** (35 KB): whole-unit reparse 0.3-0.5 ms; item-level reparse 20-50 µs. Today it measures 6.2-8.5 ms.

**Reasoning.** Today the front end costs ~0.88 µs (≈3,200 cycles) per token. The lexer alone already runs at 131 MB/s (trace: 3.3 ms for 433 KB), so the gap is not lexing. It is the line/item/String representation (~16 ms), the post-hoc passes (~11 ms) and the crypto identities and digests (~28 ms). The quick wins below get NovyWave to roughly 40-45 ms and TodoMVC to roughly 10-11 ms. That is still ~10x off the ceiling, and the remainder needs the representation change.

## representation_critique
- structure: AstToken { kind, lexeme: String, line, column, start, end: usize } | critique: ~64 bytes plus one heap allocation per token (73.6k on NovyWave). The lexeme duplicates source text that is already owned. Line and column are stored instead of derived. | better: SoA kind: Vec<u8> + start: Vec<u32> (+ len u16): ~5-7 bytes per token, lexeme = &src[start..end], line/col from a line-start table on demand, identifiers interned to Symbol(u32) in the lexer | evidence: boon_syntax/src/lib.rs:1863; lex_source_with_work lib.rs:5393 lexeme.to_owned()
- structure: ParserLine / ParserItem (SharedParserSymbols Vec<String>, symbol_spans Vec<(usize,usize)>, field/function/source_event/hold Option<String>, operators Vec<String>) | critique: The second and third copies of every lexeme. Parsing works on physical lines and needs three merge passes to approximate the real grammar. All of it is retained in the output artifact (AstProgram.tokens/lines/items). | better: Remove it. The parser consumes the token stream directly, and the item table (name Symbol, kind, node range) is produced as a by-product of parsing top-level declarations | evidence: boon_syntax/src/lib.rs:1510-1535, 1267-1273; parser_lines lib.rs:5440-5484 symbols.push(token.lexeme.clone()); lines.clone() lib.rs:4394
- structure: AstStatement { id, line, indent, start, end: usize, kind with String names, expr: Option<usize>, children: Vec<AstStatement> } | critique: A recursive boxed tree with one Vec per level, walked by at least 8 separate recursive passes (arrow contexts, linking, item index, declared functions twice, statement counts, identity visit, pack ids, validations). | better: Statements as nodes in the same flat arena with child ranges in extra_data; per-unit u32 ids | evidence: boon_syntax/src/lib.rs:1558-1593
- structure: AstExpr { id, line, start, end: usize, linked_input: Option<usize>, kind: AstExprKind } with String payloads (Identifier(String), Pipe{op: String, args: Vec<AstCallArg{name: String,..}>}, Unknown(Vec<String>)) | critique: Estimated ~150-170 bytes per node plus several heap allocations. Unknown and Delimiter nodes act as error recovery placeholders. | better: 12-16 byte nodes {kind u8, flags u8, a u32, b u32} + span arrays + extra_data u32. Enum operators and node kinds, Symbol names, explicit Error node with span | evidence: boon_syntax/src/lib.rs:1596-1757, 1802-1860
