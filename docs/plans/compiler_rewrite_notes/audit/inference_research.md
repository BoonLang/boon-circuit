## key
inference_research
## topic
Fast type inference for structural / row-polymorphic languages (Roc, Elm, OCaml, PureScript/Leijen rows, Simple-sub/MLsub, TypeScript/tsgo, Flow, Sorbet, Hack, Elixir), and what it means for redesigning Boon's type checker. Main finding: every fast system type-checks a function body once, turns its type into a generalized scheme, and at each call site only copies that scheme. Boon has no generalization step anywhere. It copies callee bodies once per call path (per chain of calls, not just per syntactic call site), and it runs each function's type as bytecode on every call. Tag-dependent WHEN arms, deferred field projections and non-monotone arm selection force that design, not the lack of annotations.
## findings
- system: Elm (Haskell compiler) | technique: The solver is constraint-based HM with ranks and pools in the Pottier/Remy HM(X) style. At `CLet` it raises the rank, solves the header in the new pool, generalizes the young pool, then solves the body. Each use of a let-bound name calls `makeCopy`, which copies only the generalized (noRank) nodes. So instantiation costs the size of the type, not the size of the body. Records are `Record1 (Map Name Variable) Variable`: fields kept sorted by name, plus an extension (row) variable. `unifyRecord` is `Map.intersectionWith`/`Map.difference` over the sorted maps. Extensible-record inference follows Leijen's scoped labels. Mutable union-find through IORef. | numbers: Solver core (Type/Solve.hs + Unify.hs + Type.hs + UnionFind.hs + Instantiate.hs) = 2,389 lines, counted with wc on fetched sources. Elm 0.19.2: 850k lines compiled from scratch in 5.7 s (about 149k lines/s for the whole compiler including codegen; core count not stated). Incremental builds under 350 ms. Community reports for 0.19.0: 50k-194k LOC full builds in 5-21 s. | relevance_to_boon: Elm is the closest well-engineered analogue: structural records with row variables, unannotated polymorphic functions, no per-call re-check. A Boon checker built this way is roughly a 2-5k-line core, against today's 81k-line kernel plus the live part of the 109k-line boon_typecheck (the plan says ~58k of it is cfg-gated). The plan's claim that full polymorphism forces per-call-path instantiation is false: Elm infers the same unannotated polymorphism without it. | source: github.com/elm/compiler compiler/src/Type/Solve.hs:157-192 (CLet/generalize), :99 and :574-582 (makeCopy at CLocal); Type/Type.hs:85 (Record1); Type/Unify.hs:613-618 (unifyRecord); https://www.developersdigest.tech/blog/elm-1-0-roadmap-faster-builds ; https://discourse.elm-lang.org/t/how-are-0-19-compile-times-for-50k-loc-projects/3680
- system: OCaml | technique: Remy's level-based generalization. Each type variable carries the let-depth where it was created. Unifying with an outer variable lowers the level. Generalizing quantifies the variables whose level is above the current one, without scanning the environment. Quantified nodes get `generic_level`, so `instance` only walks and copies generic-level subtrees and shares the rest. Kiselyov's `sound_lazy` defers the occurs check and level updates into a queue, which makes binding a variable constant time. Polymorphic-variant rows are sorted by label and merged linearly (`merge_rf`), but `merge_row_fields` re-sorts both rows on every merge. | numbers: Generalization by environment scan made early Caml type checking quadratic. Remy's anecdote: a few hundred lines took about 20 minutes to type check. Across opam packages, typing is a median 39.7% of compile time (Gagallium, 1.6M data points). | relevance_to_boon: Levels are what turn let-polymorphism into near-linear work. Boon's kernel has no levels and no generalization: 0 matches for 'generaliz' in crates/boon_typecheck/src and crates/boon_compiler_kernel/src. The row merge is the model for record and tag unification: O(n+m) on rows stored pre-sorted (OCaml pays O(n log n) because it re-sorts on each merge). | source: https://okmij.org/ftp/ML/generalization.html ; ocaml/typing/ctype.ml:663-679 (sort_row_fields/merge_rf), btype.ml:100 (generic_level); https://cambium.inria.fr/blog/measuring-compilation-time/
- system: Roc (new Zig compiler), checking | technique: Top-level definitions are checked as binding groups: the SCC condensation of the name-reference graph, in topological order. A reference between groups always points at an already-generalized definition, and checkDef is never re-entered in the middle of a body. Rank-based generalization lives in types/generalize.zig. The docs state 'each use freshly instantiates its type'. `instantiateTypeScheme` computes generalized reachability once and copies only the generalized descendants. Representation: `Var = enum(u32)`, a `Descriptor` that tests assert is 32 bytes, `RecordField` 12 bytes, rank u8, a mutable union-find store with an undo trail for speculation. Record and tag rows are ordered by exact lexicographic name ranks (u32), with radix ordering for large sets. A CI lint rejects any HashMap keyed by a dense `...Id` ('the size of the owning ID domain is not a reason to hash an ID'). A generalized scheme is a pair: the root type plus the unresolved requirements (static dispatch), instantiated per use. | numbers: Cautionary numbers: on a 27-package stress app, type inference was about 2.5 s, the largest phase (41k-line package plus a 166k-line byte-list font). Causes: row operations that copy or sort fields on every unification, an AutoHashMap allocated per `varContainsError` call, occurs checks (issue #11615). Separately, `roc check` on a 2,000-function app took 1.6 s: 31.9% in canonical type-key `writeVar` and 24.6% in SHA-256, because every published root re-hashed its whole subtree. The fix is Merkle composition over closed acyclic children (issue #11348). | relevance_to_boon: The architecture is right: SCC order, generalize once, instantiate per use, requirements carried in the scheme. Roc also shows how to lose the gains: sorting rows during each unification, and cryptographic hashing of types on the hot path. Boon does both today: intern_object sorts on every call (term.rs:2352-2386), and the plan notes CBOR+SHA-256 in the semantic phase. Boon's 'requirement backflow' corresponds to Roc's 'pending dispatch requirements in type schemes'. | source: roc-lang/roc src/check/Check.zig:345, :429-437; src/types/generalize.zig:1-45; src/types/instantiate.zig:501-535; src/types/types.zig:35, :82, :848; design.md 'Dense IDs and structural keys' and 'Pending Dispatch Requirements In Type Schemes' (line ~7829); https://github.com/roc-lang/roc/issues/11615 ; https://github.com/roc-lang/roc/issues/11348
- system: Roc: specialization, lambda sets, abilities | technique: Type checking never specializes. Monotype IR is root-driven after checking: a call to a checked procedure template 'creates or reuses the specialization keyed by the instantiated monomorphic function type', and a queue runs until no new keys appear. The key is the checked callable identity plus the requested function-type digest. It is never built from a lowered body. Checked bodies stay immutable. Lambda sets (the set of closures that can reach a function-typed position) are inferred by unification: set union, with captures unified. Later stages defunctionalize into tag unions with dispatch switches. | numbers: No published compile-time numbers for the specialization stage alone. On the issue #11615 stress app, 'Shared Monotype Lowering' took about 2,080 ms, next to 2,500 ms of type inference. | relevance_to_boon: Boon's static_variants, syntax_selected and initial_state_surface information is per-call-site specialization data. It belongs in a post-check, root-driven queue keyed by (definition, arm-selection bitset, argument TypeIds), not inside inference. Callbacks passed with OUT (e.g. `List/map(new: ...)`) are lambda-set territory: track the set of callable ids in the function type instead of inlining the callee per path. | source: roc-lang/roc design.md '## Monotype IR' (line ~10081) and '### Monotype Specialization' (line ~11334); design/lambda-set-specialization.md sections 1-2; https://dl.acm.org/doi/10.1145/3591260
- system: Simple-sub / MLsub (algebraic subtyping, Parreaux/Dolan) | technique: Principal type inference with subtyping, unions and intersections. It looks like algorithm W, but type variables carry mutable upper and lower bounds. A cache of (lhs, rhs) pairs already constrained prevents infinite recursion on cyclic bounds and 'avoids repeating identical work... important to avoid making the algorithm exponential' (Pierce 21.10). Let-polymorphism uses levels plus 'extrusion' (copying a variable that escapes to a lower level). Simplification by co-occurrence and hash-consing is the expensive, optional part. Simpler-sub unifies var-to-var constraints immediately and drops nested let polymorphism to stay near HM cost. A 2024 paper extends Simple-sub with row variables for extensible records. | numbers: Implementation is under 500 LOC including parsing, simplification and printing. It was evaluated for agreement with MLsub on 1M random expressions; no throughput numbers are published. | relevance_to_boon: Boon's kernel already has join semantics: `TypeTerm::Union`, `structural_widen`, variant-set merge (term.rs:1532, :1569). If joins must stay in the language, Simple-sub gives a principal scheme once per definition in place of per-call summary bytecode. Its constraint cache is the principled form of the ad-hoc memos the plan keeps adding (T0 and T1a). | source: https://infoscience.epfl.ch/record/278576 (paper text §3.2.2, §3.5.1); https://lptk.github.io/programming/2020/03/26/demystifying-mlsub.html ; https://github.com/LPTK/simpler-sub ; https://arxiv.org/abs/2407.06747
- system: HM complexity theory (Mairson; Kfoury-Tiuryn-Urzyczyn; McAllester) | technique: Deciding ML typability is DEXPTIME-complete: nested lets can double type size at each level. In practice it is linear: with bounded type size and bounded let-nesting depth, constraints are generated and solved in linear time (quasi-linear with recursive types). Rows add a sorted-merge cost per record unification, O(n+m) with pre-sorted fields. Scoped labels (Leijen) keep principal unification without 'lacks' predicates. | numbers: Worst case exponential; with bounded type size and let depth, linear time (McAllester 2003). | relevance_to_boon: Boon's per-call-path expansion pays the pathological cost unconditionally. The expansion factor grows with call depth (max_call_depth 12 on TodoMVC, 22 on NovyWave). Generalize-once makes cost proportional to program size plus the sum of instantiated scheme sizes. | source: http://gallium.inria.fr/~fpottier/publis/emlti-final.pdf ; https://link.springer.com/chapter/10.1007/3-540-44881-0_31 ; https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/scopedlabels.pdf
- system: TypeScript / tsgo (Go port) | technique: Structural relations are cached by a key built from the type-id pair and flags (`getRelationKey`), in per-relation maps. Recursion guards: a 'maybeKeys' in-progress set, `isDeeplyNestedType` with depth 3, a relation stack cap of 100. Hard complexity caps: union cross-product over 1,000,000 is rejected, instantiation depth 100, 5,000,000 instantiations. Interfaces are cached by identity and intersections are not; union reduction is pairwise, so quadratic. tsgo keeps the same algorithms. The gain comes from native code, parallel parse/bind and several checkers over a shared immutable AST. | numbers: VS Code 1,505k LOC: 77.8 s to 7.5 s (10.4x; about 200k lines/s, parallel). Playwright 356k: 11.1 s to 1.1 s. date-fns 104k: 6.5 s to 0.7 s. rxjs 2.1k: 1.1 s to 0.1 s (fixed overhead dominates). Secondary sources split the gain as about 3x native, 3-4x parallel parse, about 3x from the default 4 checkers. | relevance_to_boon: Boon's KernelSummaryProgram with Select arms is TypeScript-style type-level computation: a function's result type is computed by running a program on its argument types. That class needs cache keys over hash-consed type ids plus hard caps, or a finite lattice. The tsgo port also shows that changing language or runtime buys a constant factor at best. Boon is already native Rust, so any 10-100x must come from algorithms. | source: microsoft/typescript-go internal/checker/checker.go:17723 (getRelationKey), :22225 (instantiation depth/count); internal/checker/relater.go:99-110, :3121-3152, :3133, :5040; https://devblogs.microsoft.com/typescript/typescript-native-port/ ; https://github.com/microsoft/TypeScript/wiki/Performance
- system: Flow: types-first and Local Type Inference | technique: Types-first requires full annotations at module boundaries. It extracts a signature per file, checks files in parallel against dependency signatures only, and never re-checks dependencies of a changed file. LTI (default since 0.199) replaced global inference, which caused 'action-at-a-distance' behaviour and non-linear cost amplification, with local inference plus required annotations on function parameters. | numbers: 'Make IDE services and rechecks multiple times faster'. Scaled past 10M+ LOC. The classic mode suffered memory blowups, long GC pauses, 'amplification of non-linear time complexity', and low parallelism. | relevance_to_boon: Boon does not need annotations to get the same firewall. A modular per-SCC inferred scheme is the signature. What Flow abandoned is exactly Boon's current architecture: one global graph solved after inlining everything (plan T6: 'the kernel compiles every definition into one global graph before solving'). | source: https://medium.com/flow-type/types-first-a-scalable-new-architecture-for-flow-3d8c7ba1d4eb ; https://medium.com/flow-type/local-type-inference-for-flow-aaa65d071347 ; https://www.infoq.com/news/2021/09/flow-facebook-not-js-with-types/
- system: Sorbet (Ruby, C++) | technique: Local-only, forward-only inference: one pass over each method's CFG, with no type-variable unification across methods. Method signatures are the firewall. 32-bit Ref indexes instead of pointers, interned NameRef/SymbolRef compared as integers, flat arrays in GlobalState, inline small vectors, flat hash maps. Error messages are built lazily (formatting only when reported). Parallel over methods with read-only GlobalState. The LSP fast path re-typechecks only the edited file when an edit changes a method body only. | numbers: About 100,000 lines of code per second per core, scaling linearly across cores. | relevance_to_boon: Two direct lessons. Build diagnostic text lazily: Boon's kernel carries DiagnosticText and UnresolvedShape strings inside type terms (term.rs:466, TypeTerm::UnresolvedShape). And a body-only edit must be O(that definition), which is the 16.7 ms warm budget. | source: https://blog.nelhage.com/post/why-sorbet-is-fast/ ; https://sorbet.org/docs/lsp ; https://github.com/sorbet/sorbet/blob/master/docs/lsp-dev-guide.md
- system: Hack (hh_server) | technique: Explicit signatures are required on declared methods. A declaration table is built first; after that, method bodies have no dependencies on each other and are checked independently in parallel workers over a shared-memory hash table. | numbers: Incremental checks typically under 200 ms on a codebase of hundreds of millions of lines. | relevance_to_boon: Same firewall principle as Sorbet and Flow. - system: Elixir set-theoretic types | technique: A function's type is inferred once from patterns, guards and body. Multi-clause functions get an intersection of arrows, e.g. `(integer()->integer()) and (boolean()->boolean())`. A call applies the matching arrows without re-walking the body. Lazy BDDs represent types. Deliberately, calls to other modules in the same project are assumed `dynamic()` to keep incremental compilation cheap. | numbers: No typing-phase throughput published. Their own statement: 'type inference complicates incremental compilation'. | relevance_to_boon: This is the direct model for Boon's tag-dependent WHEN results, e.g. Theme `get(request)` where each request tag (`Material[of]`, `Font[of]`, ...) returns a different record, or `Element/stripe` narrowing on `direction`. Compute an intersection-of-arrows 'case scheme' once per definition, and select arms per call by tag set. That replaces per-call interpretation of Select bytecode. | source: https://elixir.hexdocs.pm/gradual-set-theoretic-types.html ; https://elixir-lang.org/blog/2022/10/05/my-future-with-elixir-set-theoretic-types/

## recommendations_for_boon
- Replace 'compile every definition into one global graph, instantiating callee bodies per call path, then solve a propagator network' with plain modular HM plus rows. Order definitions by SCC of the reference graph (Roc Check.zig:429-437). Check each SCC once with Remy/Kiselyov levels, generalize at the SCC boundary, and at call sites instantiate only generic-level nodes (Elm makeCopy, OCaml generic_level). Call cost becomes O(|scheme|), and InvocationKey, per-call-path invocation frames and pruned_invocation_expressions (95,476 on TodoMVC) disappear.
- Give records and tag unions real row (extension) variables. Replace `Object { fields, open: bool }` (term.rs:279-282) with fields sorted by symbol lexical rank (u32) plus an extension variable. Unify by linear sorted merge, as in Elm's unifyRecord and OCaml's merge_rf. Type `x.f` eagerly as `x ~ [f: a | r]`, which deletes the deferred Projection operation (program.rs:281-285; 63,584 projection activations on TodoMVC). Type spread `[...r, b: e]` with Leijen scoped labels (or lacks constraints), so one scheme covers every caller.
- Keep tag-dependent WHEN results (Theme `get(request)`, `Element/stripe` narrowing), but compile them once into a 'case scheme': an intersection of arrows, one per arm, as Elixir does for multi-clause functions. At a call, compute the u64 bitset of tag ids in the instantiated argument type, pick the matching arms, and join only their instantiated result schemes. Memoize on (case-scheme TypeId, arm bitset), an exact semantic key. If the selector is still a free variable (possible only inside a recursive SCC), take all arms. That makes inference monotone and deletes replace_binding-driven arm switching (solver.rs:1437-1475) and requirement withdrawal (requirements.rs:1-13).
- Represent requirement backflow (callee usage constraining caller arguments) as qualified constraints stored in the generalized scheme, as in Roc's 'pending dispatch requirements in type schemes' and Haskell classes. Instantiate them per use and discharge them when the receiver becomes concrete. That removes owner/site staging, withdrawal and reschedule walks: T1 measured 154,287 schedule_variable calls and 11.83M variable visits, 92.5% of them re-visits.
- Model PASS/PASSED as an implicit row-polymorphic parameter in each scheme (`PASSED: [mode: a | r]` is added when the body reads PASSED.mode). Model the contextual hole `[]` as a kind-constrained type variable (record/list/set/map/bytes), defaulted at top level, instead of 'a fresh union-find variable for every summary invocation' (program.rs ContextualHole).
- Split the type representation in two. (a) The inference graph: mutable union-find over u32 vars, SoA descriptors of 16-32 bytes (level u16, content tag, payload index), children in flat arrays, no hashing. (b) A frozen hash-consed TypeId store for generalized schemes, closed types and exports, interned once at generalization. Scheme equality then becomes TypeId equality. Today the kernel hash-conses terms that contain variables (TERM_HAS_VARIABLE, term.rs:444) and re-resolves and re-interns them: 266,605 intern requests on TodoMVC and 308,741 on NovyWave.
- Take field order out of type identity. Canonical row = fields sorted by lexical rank. Authored order becomes a side table per construction site or definition, used for display, diagnostics and any runtime-observable ordering. This is Roc's model: 'source field order never affects memory', and declared order is 'explicit checked data'. It deletes the semantic_order half of ObjectFields equality and hash (term.rs:309-321) and the per-call re-sorting in intern_object (term.rs:2352-2386). Ask the owner whether order is ever observable beyond display.
- Raise two semantics questions with the owner before the redesign. First, `structural_widen` joins records by taking the union of their field sets (term.rs:1664-1675), and incompatible heads widen to an open empty object (term.rs:1682). Is a read of a field present in only one WHEN arm meant to type-check? If yes, model it as per-field presence variables (Remy flags; Roc's field Presence var); if no, use HM rejection or width-subtyping LUB (common fields). Second, decide whether tag-dependent return types stay a language feature, since it is the only thing that needs case schemes.
- Move call-site specialization (static_variants, syntax_selected provenance, initial_state_surface) out of inference into a post-check, root-driven queue, as Roc's Monotype does. Key it by (definition id, arm-selection bitset tuple, argument TypeIds), and treat recursion as cyclic flow that falls back to the generic instance (Lutze et al. 2025). Compute syntax_selected from the final solution instead of walking the full term DAG for every publish input during solving (plan T1: term_syntax_selected).
- Make the per-SCC generalized scheme TypeId the incremental firewall. A body-only edit re-checks that SCC; if the scheme TypeId is unchanged, dependents are not touched, as in Sorbet's fast path, Flow types-first and Hack. This is the architectural route to the 16.7 ms warm budget. It is sound in HM because callers depend only on the scheme.
- Never content-hash types (SHA-256/CBOR) on the checking hot path. Use in-process u32 ids. If cross-process keys are needed, compose them Merkle-style from the child keys of closed, acyclic subtrees (Roc #11348 lesson).
- AGENTS.md: scope the rule 'Do not grow the interpreted summary evaluator... never final result-type equality' to the summary evaluator only. In an HM redesign the evaluator is deleted, and early cutoff on equality of the generalized scheme is the standard, sound firewall. Read literally, today's rule forbids it.
- AGENTS.md plus the plan: 'work its tiers in order and attribute with a sampling profile before choosing an item' cannot justify the redesign. The TodoMVC cost is 20-30x work amplification spread over the whole architecture, not one hot function. Adopt work-amplification counters (instances per syntactic call, operations per expression) as the architectural gate, and schedule T6 before the T1-T3 micro-tiers, which optimize code the redesign deletes. The plan itself says cold budgets 'are still not reachable without T6'.
- Plan §5 Q2 claims 'every function is fully polymorphic, which is what forces per-call-path instantiation'. That is wrong: Elm, OCaml and Roc infer unannotated polymorphic functions and never instantiate bodies per call. Optional FUNCTION annotations are not needed for speed. What forces per-path work is: no generalization, deferred projections without row variables, non-monotone tag-dependent Select, and PASSED flowing per path.
- Gating: a checker rewrite will change diagnostic order and text and possibly type display. Run it under a declared digest-migration lane with a semantic oracle (types equal modulo alpha-renaming and field order; same accept/reject set on the corpus) instead of byte-identical diagnostics_fingerprint_v1. Otherwise the byte-identity gate blocks any real redesign.
- Size sanity check for the rewrite: Elm's solver core is about 2.4k lines and Simple-sub under 500 LOC, against 81k lines in boon_compiler_kernel plus the live part of boon_typecheck. Aim for a 3-6k-line checker core with rows, case schemes and qualified requirements, and delete the propagator/summary/receipt machinery rather than wrapping it.
