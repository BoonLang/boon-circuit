incremental_research
## topic
Incremental / warm compilation and editor-latency architectures: what Boon needs to reach warm edit-to-diagnostics under 16.7 ms and warm verified preview under 100 ms (TodoMVC 3.6k lines, NovyWave 12k lines, multi-file)

- system: rust-analyzer / salsa | technique: Split signatures from bodies: body-insensitive ItemTree and DefMap act as a firewall, so an edit inside a body never invalidates global derived data. Red-green revisions with backdating: re-executed queries with equal output keep changed_at. Laziness: only demanded queries run. Cancellation: a revision bump makes readers unwind with Cancelled. | numbers: matklad: 'It's not the incrementality that makes an IDE fast. Rather, it's laziness'. Before durability, re-validating the standard-library query graph cost about 300 ms per edit even when nothing re-executed. | relevance_to_boon: Boon has the syntax half: StableItemRoute and UnitItemIndex (boon_syntax/src/lib.rs:525-600) is an ItemTree analogue, and boon_compilation_db already backdates (lib.rs:59-64). The 300 ms validation lesson says to keep the dependency graph coarse (per owner, about 155 on TodoMVC and 1,389 on NovyWave) and to put builtins, Theme and Generated units on high durability. | source: https://rust-analyzer.github.io/book/contributing/architecture.html ; https://salsa-rs.github.io/salsa/reference/algorithm.html ; https://rust-analyzer.github.io/blog/2023/07/24/durable-incrementality.html ; https://rust-analyzer.github.io/blog/2020/07/20/three-architectures-for-responsive-ide.html
- system: salsa tracked/interned structs; Nominal Adapton | technique: Stable identity across revisions comes from content: a tracked struct's identity is (creating query, #[id] fields, disambiguator). Adapton argues that first-class names identify which computations to reuse across runs, and proves results are 'from-scratch consistent' (same answer as a full recompute). | numbers: Jane Street Incremental: about 30 ns per graph node is the break-even overhead (secondary source). | relevance_to_boon: Boon's parser routes already avoid offsets and dense ids. - system: Zig incremental compilation | technique: The unit of analysis is the AnalUnit: struct layout, declaration type, const value, function body. A dependency graph records typed 'dependees': src_hash (a 128-bit hash of each declaration's ZIR region), namespace and namespace_name, nav_val, func_ies and interned types. After AstGen, units hit by changed hashes are outdated and their dependents are 'potentially outdated' (PO) with a PO dependency count. When a PO dependee turns out up-to-date the count drops, and at 0 the unit is skipped (early cutoff). InternPool indices are immutable: an old Index stays valid and a changed type gets a new index. Old-to-new ZIR instruction mapping (TrackedInst) gives stable identity. Codegen is per function, and the linker patches bytes in place. | numbers: 0.14: a 500k-line codebase takes 14 s cold and 63 ms after an edit (compile errors only, -Dno-bin). Compiler state serialization is not implemented, so it relies on a resident --watch process. Fizzy editor: 37 ms incremental rebuild, of which about 1.6 ms is the core pipeline and about 30 ms is resolveReferencesInner, a whole-graph traversal that 'did not even need to run'. 0.16: about 30 ms incremental rebuilds with the self-hosted ELF linker. | relevance_to_boon: This is the closest model for Boon: per-owner units, typed dependee tables instead of a generic query walk, and interning by content. Fizzy shows that a single O(program) pass dominates warm latency. Boon has at least five such passes (abi, projection, input, compile, solve) before any reuse decision. | source: https://ziglang.org/download/0.14.0/release-notes.html ; https://gist.github.com/mlugg/73b3e60c803006f3556d87c9ed3e8a0e ; https://www.developersdigest.tech/blog/zig-incremental-compilation-internals-hn-analysis (secondary summary of https://mlugg.co.uk/posts/incremental-compilation-internals/, which returned 403)
- system: Sorbet | technique: LSP fast path: the edited file is indexed and resolved against an empty local GlobalState and its symbols are hashed into LocalSymbolTableHashes. hierarchyHash decides fast or slow path. Per-name SymbolHash vectors are set-differenced, and only files whose UsageHash mentions a changed name are rechecked (a deliberate over-approximation by name). FileHash must contain nothing specific to a GlobalState: names are hashed, not stored as ids. Inference is local only, and every symbol in the global table needs an explicit signature. | numbers: About 100,000 lines/s per core on Stripe's codebase. | relevance_to_boon: This fingerprint discipline is exactly what packed_owner.rs:196 owner_program_fingerprint breaks, because it hashes content that depends on global term-store numbering. Boon has no signatures, so its 'signature hash' has to be the canonical hash of the inferred interface, computed as a by-product of checking the owner. | source: https://github.com/sorbet/sorbet/blob/master/core/FileHash.h (comments on LocalSymbolTableHashes, UsageHash, FileHash) ; https://blog.nelhage.com/post/why-sorbet-is-fast/
- system: Hack (hh_server) | technique: Fanout comes from shallow declaration diffs at member granularity: member_change is Added, Removed, Changed_inheritance, Modified or Private_change_not_in_trait. Fanout.t separates changed decls from to_recheck (dependents via symbol-hash deps), and adds to_recheck_if_errors only for files that previously had errors. Declarations with only position changes are excluded, and files whose analysis would differ only in positions are not rechecked (only their stale error positions are refreshed). | numbers: none published in the files read | relevance_to_boon: Store records are Boon's classes. Adding the field `pinned` to a row should fan out only to readers whose instantiation actually depends on the row shape, not to every owner. Position-only rechecks require owner-relative spans. | source: https://github.com/facebook/hhvm/blob/master/hphp/hack/src/decl/fanout.mli ; .../decl/class_diff.mli ; .../server/server_incremental.mli
- system: rustc incremental; Roslyn | technique: rustc hashes spans relative to the enclosing item, so a body edit in one function does not invalidate others through span changes. Roslyn green nodes are immutable, store widths instead of positions and have no parent pointers, so an edit rebuilds O(log n) nodes. Red nodes are an ephemeral facade that computes absolute positions on demand. | numbers: O(log n) green nodes rebuilt per edit | relevance_to_boon: Boon's AST stores absolute positions and file-global ids. Inserting a line at the top of NovyView.bn shifts every node below it, so nothing keyed on AST ids or spans can survive the edit. Item-relative spans and item-local ids are a prerequisite for per-owner reuse. | source: https://github.com/rust-lang/rust/pull/143882 ; https://ericlippert.com/2012/06/08/red-green-trees/
- system: Kotlin K2 / Analysis API (LL FIR) | technique: Resolution runs lazily per declaration and per phase (SUPER_TYPES, TYPES, ..., BODY_RESOLVE). A PSI change is either in-block (only the declaration is re-resolved) or out-of-block (OOBM, which invalidates module caches). The rule is syntactic: `KtNamedFunction.isReanalyzableContainer() = hasBlockBody() || typeReference != null`, and a property initializer is never reanalyzable. | numbers: LLFirDeclarationModificationService.kt:584-588 | relevance_to_boon: Kotlin firewalls bodies only when a type is declared. In Kotlin's terms every Boon edit is out-of-block, because FUNCTIONs and store bindings are unannotated expressions. Boon therefore needs semantic firewalls: infer the owner's interface, compare fingerprints and backdate. The alternative is the owner's open question on optional annotations acting as firewalls. | source: https://github.com/JetBrains/kotlin/blob/master/analysis/low-level-api-fir/src/org/jetbrains/kotlin/analysis/low/level/api/fir/file/structure/LLFirDeclarationModificationService.kt ; https://blog.jetbrains.com/idea/2025/04/the-story-behind-k2-mode-and-how-it-works/
- system: Swift request evaluator / dependency analysis | technique: Requests are self-contained and cached, with an evaluator-maintained stack for dependency tracking and cycle diagnostics. Incremental dependencies come from instrumenting lookups: 'dependency sources' (file-level requests) collect names looked up by 'dependency sinks'. Dependency kinds are top-level, nominal, member and dynamic-lookup. Golden rule from the doc: 'The golden rule of dependency analysis is to be conservative.' | numbers: n/a | relevance_to_boon: Record each owner's dependencies by instrumenting name resolution and field or PASSED lookups inside that owner's inference. This gives the reverse edges for fanout without a separate whole-program pass. | source: https://github.com/swiftlang/swift/blob/main/docs/RequestEvaluator.md ; https://github.com/swiftlang/swift/blob/main/docs/DependencyAnalysis.md
- system: TypeScript builder / tsgo | technique: The builder stores each file's signature (the shape of its .d.ts). Affected-file search walks dependents breadth-first and stops once signatures stabilize, and the state is persisted in .tsbuildinfo. The tsgo language service uses immutable, ref-counted snapshots cloned per change, a parse cache, and a checker pool with one dedicated diagnostics checker plus query checkers. The checker itself is not incremental; it is fast and lazy (checks what open files need). | numbers: Issue #64464: the first incremental edit after a clean build took 34.3 s vs 0.57 s for a full check, because signatures were computed through a separate declaration emit (79% of CPU in getAlternativeContainingModules). The Go port is about 10x faster (VS Code 1.5M lines: about 78 s to 7.5 s). | relevance_to_boon: The interface fingerprint must fall out of checking the owner, never come from a separate emit or whole-program pass. #64464 is what happens otherwise, and T5's plan to fingerprint the packed program after projection is the same mistake. The immutable-snapshot pattern is how edits get applied while a compile is still running. | source: https://github.com/microsoft/TypeScript/blob/main/src/compiler/builder.ts ; https://github.com/microsoft/TypeScript/issues/64464 ; https://github.com/microsoft/typescript-go/blob/main/internal/project/snapshot.go ; .../internal/project/checkerpool.go ; https://dev.to/grimicorn/typescript-70-the-go-compiler-that-makes-ts-10x-faster-4al6
- system: Carbon toolchain | technique: Data-oriented design: vectorized storage with int32 indices instead of pointers, flyweights passed around, parse tree as a flat SmallVector. There is no incrementality; the bet is raw throughput. | numbers: Stated goals: 10M lines/s lex+parse and 1M lines/s semantic checking on one core (Carruth, CppNow 2023 / NDC Toronto 2026). | relevance_to_boon: At 1M lines/s a full recheck of TodoMVC is about 3.6 ms and of NovyWave about 12 ms, inside the warm budget with no incrementality. At Sorbet's 100k lines/s TodoMVC would be about 36 ms. Boon's check runs about 9.7k lines/s, roughly 100x off Carbon's target. A fast cold path is what bounds worst-case edits to hub owners such as a store type change, which incrementality alone cannot help. | source: https://docs.carbon-lang.dev/toolchain/docs/ ; https://www.youtube.com/watch?v=ZI198eFghJk ; https://daily.dev/posts/benchmarking-and-optimizing-the-carbon-compiler---chandler-carruth---ndc-toronto-2026-i4ljgsvpo
- system: Lean 4 server | technique: The full elaboration state is snapshotted after each command, and elaboration restarts at the first changed command. - system: Elm / Gleam / Roc | technique: Elm and Gleam cache per module: Gleam's .cache_meta stores mtime and imports and recompiles a module if any upstream module recompiles; Elm cascades to importers. ## anti_patterns_seen_in_boon
- crates/boon_compiler/src/session.rs:485-486: every apply_update sets state.diagnostics = None and state.checked = None, so the only cross-revision reuse is per-file parse. Measured warm diagnostics equals cold typecheck: 377.6 ms vs 370 ms.
- crates/boon_compiler_kernel/src/session.rs:738-751: replace_project drops prepared, solved and checks; the doc comment at :700-705 says red/green reuse 'is' future work. replace_project also has no production caller: kernel_oracle.rs:1279, 2443 and 2891 build a fresh KernelSession::new(input) for every request.
- crates/boon_compiler/src/session.rs:787: `state.checked.take()` consumes the checked result into the verified path. Diagnostics (kernel_oracle.rs:2375) and verified (kernel_oracle.rs:2837) are separate kernel solves, so the warm preview re-solves the revision diagnostics just solved: 456 ms typecheck in the preview phase on TodoMVC, 705-729 ms on NovyWave.
- crates/boon_cli/src/compiler_sample.rs:1080-1086: the scored warm edit alternates forward and reverse (A->B->A->B), so a 2-entry content-addressed cache would pass it with no incremental architecture. The benchmark requests CompileIntent::Diagnostics (:1099) while the playground product path requests EditorDiagnostics (crates/boon_native_playground/src/compile.rs:540) and then VerifiedPreview (:598). The only budgeted edit class is one text literal.
- crates/boon_syntax/src/lib.rs:1596-1603: AstExpr carries absolute line/start/end plus a file-global dense `id: usize`, so any edit shifts every later node's identity and span in the unit. rustc (relative spans), Roslyn (width-only green nodes) and Hack (positions-only changes are not rechecked) all avoid this.
- crates/boon_compiler_kernel/src/packed_owner.rs:196 owner_program_fingerprint: per docs/plans/evidence/compiler-m4-reuse-key-2026-09-28.json, 86 of 109 distinct owner fingerprints change after adding one field to one row, because the shared term store renumbers on append. Sorbet's FileHash.h forbids GlobalState-specific ids in fingerprints for exactly this reason.
- docs/plans/BOON_COMPILER_PROFILE_DRIVEN_PLAN_2026_09_28.md:217-223 (T5.1): the reuse key is owner_program_fingerprint, which exists only after whole-program ABI, projection and KernelProjectInput construction. Measured before any reuse decision: parse 6.8 + abi 1.1 + projection 17.2 + input 11.5 = 36.6 ms on TodoMVC and about 35 + 9.1 + 83.5 + 47.5 = 175 ms on NovyWave. The plan's '~10-25 ms' warm estimate cannot hold with that key. Reuse is also all-or-nothing: any type-relevant edit falls back to a full cold solve.
- crates/boon_compiler/src/session.rs:870 (inside parse_project_syntax_snapshot) and crates/boon_parser/src/lib.rs:2101: a unit's first parse error aborts the whole project request (ParseError holds a single message and there is no recovery). While a user types, most keystroke states are syntax errors, and project-wide type diagnostics and preview updates vanish.
- crates/boon_compiler_kernel/src/session.rs:883-884: CheckDemand::Definitions calls ensure_solved() on the whole graph, then filters. There is no lazy, demand-driven path.
- grep -i cancel finds zero checkpoints in crates/boon_compiler_kernel/src (the only hits are the Boon tag 'Cancelled' in term.rs) and zero in crates/boon_semantic/src. A 280 ms solve or a 780 ms NovyWave semantic pass cannot be preempted by a new keystroke.
- crates/boon_compiler/src/kernel_oracle.rs:3091-3102 runs the EditorRich parity oracle in production on every editor request, and :3105-3119 re-runs the whole checked construction when a RuntimePacked request hits an error, doubling the cost of error revisions, which are the common state while typing.
- AGENTS.md:38 ('never final result-type equality') is ambiguous against salsa-style backdating, which compares a query's new output to its old one to keep changed_at. boon_compilation_db already does this (lib.rs:59-64). AGENTS.md:44 ('do not reopen ... summary memoization') forbids per-definition summary reuse, which is the core of every fast incremental checker for unannotated polymorphic code. AGENTS.md:32 mandates a cold two-lane 3+30 protocol that does not measure warm architecture changes.
- budgets/compiler.toml machine_plan_sha256 pins a byte-exact monolithic plan, and AGENTS.md:33-34 forbids editing budgets. A per-owner relinked plan that is semantically identical but laid out differently cannot land without an explicit digest-migration path.
## recommendations_for_boon
- Fix the benchmark first, or everything after is Goodhart. Replace the A/B/A/B literal toggle with monotonic keystroke sequences on the product path (EditorDiagnostics then VerifiedPreview). Report p95 per edit class: whitespace or comment; literal; body change that keeps the type; interface change (add a row field, change a WHEN tag set); add, remove and rename a definition; intermediate syntax-error states (type 'Walk the dogs' one character at a time, including an unclosed brace); a multi-file NovyWave edit in View/NovyView.bn. Add an in-flight cancellation probe (cancel 5 ms into a solve).
- Make the owner the unit of reuse: every StableOwnerKey (functions and also store fields, holds, lists and sources), interned once to a session-stable u32 OwnerId that is never renumbered (tombstone on delete), in the style of Zig's TrackedInst and salsa interning. Carry OwnerId through kernel, semantic and plan. Ban dense or insertion-order ids and global term indices from any cross-revision key; hash types by content, as Zig's InternPool and Sorbet's FileHash do.
- Parse incrementally at item level. Split units at top-level item boundaries (column-0 FUNCTION or name:), reparse only the touched item, and store item-relative spans and item-local node ids. Emit per-item fingerprints as a by-product of the parse: header_fp (name, params, kind), shape_fp (tokens and AST with literal values masked but literal kinds kept), and literal_fp. Recover errors at item granularity: a broken item keeps its last-good interface and reports only its own syntax error. Target 1 ms or less per edit; NovyView costs 34-37 ms today.
- Replace per-call-path global solving with per-owner inference in call-graph order. Recursion is rejected in v1 (docs/plans/TYPE_INFERENCE_AND_TYPECHECKING_PLAN.md:283, 488), so there are no SCCs to solve. Each owner produces an Interface (a principal summary: scheme over parameters plus row-polymorphic PASSED requirements plus stream kinds) and local diagnostics. Where static selector pruning or context-dependent arms rule out a closed scheme, memoize instances by the exact interned argument/PASSED/selector tuple, as Zig does for generic instances. Measured headroom: 414 distinct specialization plans vs 10,537 compiled call sites on TodoMVC. This is the T6 restructure; it is the warm architecture, not optional research.
- Use explicit Zig-style dependee tables instead of a generic query-graph walk. Dependee kinds: OwnerShape, OwnerLiterals, Interface(owner), Name(module, name), Instance(owner, tuple), BuiltinAbi (high durability). On each edit: mark owners outdated by source fingerprints, mark dependents potentially outdated (PO) with counts, re-infer outdated owners, and backdate the Interface when its canonical 128-bit content hash (alpha-normalized type variables) is unchanged. A PO count reaching 0 skips the owner. Record dependencies by instrumenting name and field lookups during each owner's inference (Swift sources/sinks), and diff interfaces at record-field granularity (Hack member diffs).
- Add a literal fast path as a first-class edit class, not a benchmark hack. The kernel already keeps literal payloads out of the type equations (boon_compiler_kernel/src/owner.rs:742-748). When only literal_fp changes, skip typing entirely, patch the literal rows in the retained checked image and the plan's constant pool, update the Merkle hash, and let the runtime hot-swap constants. TodoMVC's theme files hold 1,078 numeric literals; live UI tuning is literal editing.
- Retain one per-owner artifact store across revisions and intents: syntax, interface, diagnostics, instances and lowered fragments. Remove `state.checked.take()` and the per-request KernelSession::new calls; Diagnostics, EditorDiagnostics and Verified must share one solve. Store diagnostics owner-relative, publish deltas, and compute absolute positions at presentation time, so an edit that only moves positions triggers no recheck.
- Make the back half per owner-instance. Lower fragments keyed by (shape_fp, dependency interface fingerprints, instance tuple). Build the MachinePlan by a thin link that concatenates and relocates fragments (the Zig incremental linker patches bytes in place), with plan_sha256 as a Merkle root over fragment hashes. Consider a dev-preview record representation that does not depend on layout, so adding a field does not force re-lowering every reader (estimate).
- Move proof off the latency path but keep it continuous. In-process plans get a trusted seal. A background oracle runs on idle (about 300-500 ms after the last edit): full cold pipeline, verify_plan, and a from-scratch-vs-incremental digest comparison, which is Adapton's from-scratch consistency property. On a mismatch it publishes the from-scratch result and files a bug. This matches Sorbet's slow path and rust-analyzer's flycheck.
- Concurrency and cancellation: build an immutable snapshot per revision (tsgo snapshot.go, rust-analyzer Analysis) so edits apply while a compile runs. Check a revision-scoped cancel flag at every owner boundary and every few thousand solver operations. Keep completed per-owner results from cancelled revisions and revalidate them next time (salsa semantics). Schedule in priority order: edited owner's diagnostics, then dependents, then preview, streaming results as a Lean-style snapshot tree.
- Last-good publication at owner granularity: an owner with errors contributes its last-good interface to dependents, which prevents cascades, and its last-good fragment to the preview when interfaces are compatible. Neither diagnostics nor preview should ever blank project-wide over a local error.
- Persistence comes last. Once warm reuse is correct, serialize per-owner artifacts keyed by content fingerprints plus the compiler build id, in an index-only relocatable layout (Roc) so loading is mmap or memcpy, and report 'cached cold' separately from true cold. Zig shipped 63 ms warm rebuilds without state serialization, so the warm budgets do not depend on this.
- Do not rely on incrementality alone. Worst-case edits to hub owners (store row types reach every contextual function through PASS) degrade to cold. Pair this work with raw cold-path speed (at least 100k lines/s check, per Sorbet; Carbon targets 1M lines/s), because the per-owner design is also the cold design: cold is warm with an empty store.
