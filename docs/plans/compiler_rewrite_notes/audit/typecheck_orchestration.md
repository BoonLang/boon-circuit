## key
typecheck_orchestration
## subsystem
Typecheck phase orchestration: everything between parse and semantic, i.e. owner projection, kernel input packing, KernelSession, solve demands, diagnostics, RuntimePacked vs EditorRich materialization, checked-image publication, sealing and the handoff to semantic (boon_compiler/src/lib.rs, kernel_oracle.rs, session.rs, boon_typecheck release surface, boon_checked publication)
## purpose_summary
In the product path, "typecheck" is a chain of conversions around one kernel solve. Both intents start the same way (kernel_oracle.rs:2375 for diagnostics, :2837 for verified). First, whole-project syntax walks build side tables keyed by String: source payload types, source paths, value surfaces, the builtin plus user ABI, and callable surfaces. Then each of the 163 (TodoMVC) or 1,397 (NovyWave) owners goes through a ~1,500-line projection (compact_owner_view, :5580). Its output is a rich PreparedOwner linked by StableCheckOwnerKey (Arc<str> plus Vec<Vec<String>> routes). A dependency-pruning fixpoint left over from the migration then runs, and all cross-owner references are relinked from stable keys to dense ids (:680-1200). KernelProjectInput::new_with_abi (kernel session.rs:238) then does another round of work. It walks every rich string again to rebuild the text catalog. It walks it a third time to validate, re-validates the linker facts (recomputing every parser call-site SHA digest), SHA-256-hashes the whole rich input per owner (V14 basis), and packs everything a second time. The kernel then compiles a global equation graph and solves it. After that the two intents split. Diagnostics solves the 'interface cone' and presents diagnostics. Verified solves everything and then runs a publication chain. That chain finalizes into DefinitionCode with four SHA-256 currentness receipts per definition. It re-materializes rich CheckedProgramFields rows with boon_checked::Type trees. It builds an 'independent' ownership plan plus a checked-image publication that duplicates the same loops. It CBOR+SHA-seals each definition key, re-derives lowering metadata from rows plus syntax, freezes the publication and hashes the metadata. Then, inside finish_checked_machine_plan and still charged to typecheck_ms (lib.rs:1311-1319), it seals a CheckedImageHandoffV4: one CBOR+SHA per projection (640 on TodoMVC, 3,090 on NovyWave), a pairing receipt and flow-term handoff, and a separately sealed packed KernelSemanticInputV1. Semantic receives two representations of the same checked program and cross-validates them (boon_semantic/src/lib.rs:2882-2920). The CompilerSession never shares a solve between intents or revisions: each request builds a new KernelSession (kernel_oracle.rs:2443, 2891), and replace_project has no production caller. Measured medians (ms). TodoMVC diagnostics 368 = projection 17 + input 11.5 + compile 59 + interface solve 278 + other 2. TodoMVC verified 431 = 1 + 17 + 11.5 + 59 + full solve 269 + finalize 39 (receipts 11) + rows 17 + metadata 5 + seals/layout/order 1.3 + present 0.6 + handoff 11. NovyWave diagnostics 461 = 9 + 84 + 47 + 81 + 237 + 2. NovyWave verified 702 = 9 + 84 + 46.5 + 81 + 199 + finalize 153.5 (receipts 43) + rows 54 + metadata 21.5 + seals/layout 4.8 + present 2 + handoff 45.7. The verified surcharge comes entirely from post-solve publication: +73 ms on TodoMVC and +279 ms on NovyWave. The full solve is actually cheaper than the diagnostics interface-cone path (269 vs 278, 199 vs 237), which is why the net gaps are +63 and +241. Only about 76% of TodoMVC verified 'typecheck' is compile+solve, and only 40% of NovyWave's. On NovyWave verified, 421 of 702 ms is orchestration and publication. The architectural split also causes a real correctness bug: the Diagnostics intent never runs list-order validation. A program with an invalid List/then_by reports 0 diagnostics with coverage=true, while verified fails on the same source.
## essential_work
- Resolve names once: identifiers and paths to local declarations, formals/PASSED, owner publics, builtins and host ABI.
- Lower each owner body once into the solver's constraint IR, with dense owner and expression ids.
- Map SOURCE payload and host-port ABI to closed types once per project.
- Look up builtin and user callable signatures. The builtin half is static and could be built once per process or at compile time.
- Generate constraints and solve: interface cone for diagnostics, full graph for verified. On these fixtures the two are nearly the same set.
- Produce one ordered, deduplicated diagnostic list from solver facts plus syntax-local rules, including the list order-chain rules, and map spans to (file, line, column).
- For verified, hand semantic one immutable view of the solved types (per-expression type ids plus call instantiations) together with the lowered owner IR.
- For warm edits, retain lowered owners and solved per-owner results keyed by content and dependency epochs, and re-solve only the dirty cone.

## from_scratch_design
One solve per revision, zero re-materialization. Every representation is keyed by u32 ids from a single persistent interner.

1) Identity and text. A process- and session-persistent, append-only Interner (SymbolId u32) is seeded at startup from a static builtin table. A process-global hash-consed TypeStore holds closed types, and the builtin ABI is a `static LazyLock<AbiTable>` with pre-interned SymbolIds and TypeIds. The parser's item index assigns each owner a slot in a generational OwnerTable keyed by a 128-bit xxh3 of (unit path, item route), so OwnerIds stay stable across revisions. Expression identity is (OwnerId, local u32). No SHA-256 or CBOR is computed for internal identities.

2) Resolve and lower in one DFS per owner, in parallel with an ordered merge for determinism. The DFS keeps a scope stack of SymbolId -> Binding. It writes SoA buffers directly in the kernel's final input format: node kind u8, input-edge range, flow mode, span (unit u16, start u32, len u32), and SymbolId/TypeId payloads. Fact tables (declarations, statements, SOURCE/HOLD/LIST, calls with resolved callee ids) are written in the same pass, together with syntax-local diagnostics. SOURCE payload and host-port tables are computed once per revision. This replaces kernel_oracle's side tables, PreparedOwner, relinking, new_with_abi rediscovery and validation, and the V14 hashing (about 7 passes and 3 representations).

3) Solve. The kernel borrows the buffers. The solver design is out of scope here, but T6's per-definition SCC scheme fits this interface. The output is `Solved { store: Arc<TypeStore>, expr_types: per-owner Vec<TypeId>, call_instantiations, interface: per-owner (formals, result) TypeIds, diagnostics }`. Order-chain validation becomes a solver diagnostic rule over call chains plus solved key types, so every intent sees it.

4) Intents. Diagnostics and verified share the same Solved value, retained in ProjectState. Diagnostics formats the diagnostics and stops. Verified moves `CheckedImage { syntax, lowered, solved }` into semantic by value; Rust ownership replaces pairing receipts, ownership expectations, seals and the V4 handoff. If semantic needs boon_checked::Type trees, it materializes them lazily through a TypeId -> Arc<Type> cache. EditorRich-only products (hover types, occurrences, call result paths) are computed per query from the same image.

5) Incremental. Retain per unit (parse, lowered owners) keyed by content hash. Retain per owner the solved interface keyed by (owner content hash, callee interface hashes). An edit re-lowers the changed unit, re-solves the dirty SCC cone, and backdates owners whose interface is unchanged. Interner and TypeStore are append-only, so retained ids stay valid.

Pass count: lex and parse (1), resolve and lower (1 per owner, parallel), constraint build and solve (1 plus the fixpoint), diagnostics (1 over sites). Verified adds 0 typecheck passes, and there are 2-3 representations instead of ~14.
## speed_ceiling
Orchestration only (everything except constraint compile and solve):
- Today: TodoMVC 30 ms diagnostics / 103 ms verified; NovyWave 142 / 421 ms.
- Measured per checked expression today: projection 4.2-5.4 us, input packing 2.8-3.0 us, rows 3.5-4.2 us, handoff 2.7-2.9 us, metadata 1.2-1.4 us, finalize up to 9.8 us on NovyWave.
- Clean design: at 150-400 ns per AST node for resolve+lower+diagnostic presentation (4.9k parsed expressions on TodoMVC, 17.7k on NovyWave) and ~0 for verified handoff, estimate 1-3 ms TodoMVC and 3-8 ms NovyWave single-threaded, ~1-3 ms NovyWave on 8 threads.
- Fixed per-compile overhead falls from ~1.7 ms (measured on a 2-line program) to <0.1 ms with static builtins.

Whole typecheck phase (estimate, depends on the solver redesign, which is outside this area):
- With a per-definition SCC solver at roughly 0.3-1 us per constraint over ~20-40k constraints, instead of today's 82k call-path-duplicated linked operations on TodoMVC, the ceiling is about 15-40 ms for TodoMVC and 25-70 ms for NovyWave.
- Diagnostics and verified would differ by <1 ms, versus 63 and 241 ms today.

Warm type-preserving single-owner edit with retention: 0.5-3 ms of typecheck, against the 16.7 ms budget.

Even without touching the solver, removing incidental orchestration and publication and sharing one solve per revision takes TodoMVC verified typecheck from 431 to ~335 ms and NovyWave from 702 to ~290-300 ms. The warm edit-to-verified-preview drops one whole typecheck (-368 / -461 ms).
