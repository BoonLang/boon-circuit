## key
engineering
## subsystem
Cross-cutting engineering across the compiler crates: hashing/digests, allocation and representation, serialization, Cargo profile/allocator, build and dev loop, crate boundaries, probes/cancellation/env reads
## purpose_summary
The pipeline goes parser, then dense kernel typecheck (driven from boon_compiler/src/kernel_oracle.rs), then rich boon_checked::Type / CheckedProgram, then boon_semantic elaboration, then boon_verify, boon_ir, the MachinePlan backend and boon_plan seal/verify. Every stage builds cryptographic "receipts", "proofs", "fingerprints" and "manifests" for what it just produced, using SHA-256 through several channels: canonical ciborium CBOR (boon_contract/src/lib.rs:28-166), a std::hash::Hasher that feeds SHA-256 (StableSha256Hasher, compiler_kernel/src/receipt.rs:3153-3240), direct Sha256::new() per type term, per expression route and per call site, and a whole-plan SHA-256 inside verify_plan (boon_plan/src/lib.rs:11497 → 14184). I counted SHA-256 compress invocations inside the timed compile window by putting a gdb breakpoint on sha2::compress256. NovyWave verified runs 1,380,688 invocations over 2,452,678 blocks, which is 157 MB hashed for a 435 KB source (361x the source bytes). A time-uniform gdb sampler independently puts sha256_compress at 24.9% of that compile. Everything that builds or validates receipts, digests or manifests together takes about 41% of NovyWave verified. The same measurements show sha256_compress was invisible in the profiles behind the active plan, because profsum.py drops zero-size asm symbols. Types move through several representations: the parser uses Strings, the kernel uses interned SymbolId/TypeTermId, then the program goes back to String-keyed BTreeMap rich types and String-heavy semantic and plan rows. So BTree, clone, drop and allocator work make up another ~25-30% (inclusive, overlapping). NovyWave verified does 7.46M allocations / 1.33 GB; 74% of allocations are 64 bytes or smaller. The release profile is lto=false, codegen-units=16, target-cpu generic, and that profile is frozen in budgets/compiler.toml. A one-crate kernel edit takes 143 s to produce a new release binary. The warm session gives essentially no typecheck reuse: TodoMVC edit-to-diagnostics is 381 ms against 390 ms cold, and the verified preview typechecks the same revision a second time. Env-var reads, probes and cancellation checks are not a CPU problem (under 0.2% of samples). But there are only 8 cancellation checkpoints per compile, so there is none inside a 370-700 ms typecheck.
## essential_work
- Read source bytes once, lex and parse into an AST (one pass over ~435 KB for NovyWave)
- Intern identifiers and paths once. Map names to definitions (name resolution / scopes)
- Type inference for unannotated FUNCTIONs: unification over dense type variables, generalization per call-graph SCC, instantiation at call sites, record/tag/list/reactive-flow types
- Diagnostics with spans (only on error paths is string formatting needed)
- Lowering the typed reactive program (HOLD/LATEST/THEN/WHEN/WHILE/LIST/SOURCE) to a dataflow IR and then to the MachinePlan the runtime executes
- One identity for the produced artifact if it is persisted or shipped (one hash of final bytes, computed on demand)
- For warm editing: per-item change detection (cheap fingerprint or structural equality of interned results) and reuse of unchanged items' solved state

## from_scratch_design
Goal: every pass is a linear sweep over flat arrays of u32-indexed POD rows, with no crypto and no per-node heap objects.

(1) Source and text. Each file is one String. A global Interner (FxHashMap<&str, Symbol(u32)> backed by one byte arena) is filled during lexing. Every later stage uses Symbol and never String. A 64-bit xxh3 of each file's bytes (435 KB at ~20 GB/s is about 0.02 ms) is the only change-detection input for parsing.

(2) Lex and parse in one pass. Tokens go into an SoA (kind: u8, start: u32). A recursive-descent/Pratt parser writes into a flat AST, Vec<Node{kind: u8, a: u32, b: u32}>, with variable-length children in one extra Vec<u32> (Zig/Carbon layout). Stable item identity is (file, item path of Symbols, sibling ordinal), stored as a u32 ItemId, and never a digest. Validation happens inside the parser (no separate validate_* passes, and no second byte scan).

(3) Resolution. One pass fills a side table Vec<DefRef> indexed by NodeId, with scopes on a stack plus an undo log.

(4) Types. A single TypeInterner hash-conses TypeKind into TypeId(u32) with FxHash + structural equality. Records are sorted (Symbol, TypeId) slices in an arena, and tags are sorted Symbol slices. Equality, dedup and ordering are integer operations. Unification is union-find over dense TypeVar(u32) arrays (ena-style) with level-based generalization. Unannotated FUNCTIONs are inferred once per call-graph SCC in dependency order, producing a scheme that call sites instantiate (no per-call-path re-walks). Substitutions are Vec<Option<TypeId>>, not BTreeMap<TypeVar, Type>. No rich Type tree exists anywhere. Diagnostics render types to strings lazily, only for errors.

(5) Lowering. The typed AST lowers directly into one dataflow IR (Vec<Op> with u32 operands and side tables for spans/debug names), then the MachinePlan is emitted directly from the IR. Debug names live in a separate table, not inline strings. Output size should be O(source nodes). The current 64,482 document expressions for TodoMVC is a red flag to investigate.

(6) Incrementality. A salsa-style query graph keyed by ItemId, with revision counters and backdating when a recomputed result is id-equal to the previous one. Fingerprints, where needed across processes, are 128-bit xxh3 computed bottom-up while building rows. Diagnostics and verified requests read the same retained solved revision.

(7) Trust. Invariant checks run under debug_assertions only. Full verify_plan runs only when loading an untrusted or persisted plan. One SHA-256 (or BLAKE3) of the final plan bytes is computed lazily when someone exports or persists it.

(8) Memory. Per-revision bump arenas and Vec<T> columns. There are no Box/Rc/String per node, so allocation count is O(number of tables): thousands, not 7.5 million.

(9) Crates. Split by pipeline stage (syntax, sema, lower, plan) with small hot accessors marked #[inline] or kept in the same crate. Legacy engines and oracles move out of library crates into a test-only crate. The shipped binary uses lto=fat, codegen-units=1, panic=abort, and PGO trained on examples/. Keep a separate fast 'perf-dev' profile (thin-local LTO, cgu=16, incremental) for iteration.

(10) Parallelism is optional (parse files and check SCC wavefronts in parallel). The single-threaded design should already meet the budgets.
## speed_ceiling
A. Engineering-only fixes inside the current architecture: drop or replace SHA and CBOR, stop receipts/manifests on the product path, lazy plan hash, dense/Fx maps, interned field names, no Debug sort keys, LTO/cgu1/PGO. Estimates built from the measured shares:
- NovyWave verified 1870 ms: remove ~465 ms SHA, ~200-300 ms of other receipt/manifest/validation construction, ~80 ms CBOR, ~100-150 ms of BTree/clone/drop/SipHash, then 10-20% from LTO+PGO (estimate). Result about 650-900 ms.
- TodoMVC verified 790 ms: minus ~170 ms SHA (72 of it the plan hash), minus receipts/BTree/clone, gives about 350-450 ms.
- TodoMVC diagnostics 390 ms: only about 17 ms SHA and small BTree/alloc shares. It is solver-bound (schedule_variable 18.2%, refresh_requirements 3.5%, invalidate_requirement_cone 3.2%, TypeTermArena::term 5.8% self), so about 300-330 ms.
- NovyWave diagnostics 526 ms: about 400-450 ms.
- Warm verified preview (TodoMVC): 1167 ms, falling to ~730 ms just by sharing the solve across intents.
So engineering alone buys ~2x on verified and ~1.2-1.3x on diagnostics. That is still 4-5x over the TodoMVC cold budgets (75/300) and ~20x over the 16.7 ms warm budget.

B. The clean design above:
- TodoMVC (~103 KB, 3.6k compiler-input lines): lex+parse 1-2 ms at 50-100 MB/s; resolve+infer 2-6 ms (~6-10k nodes at 100-500 ns per node per pass); lowering+plan emission 3-10 ms. Cold diagnostics is about 3-8 ms and cold verified about 10-25 ms. A warm edit (re-parse one unit, re-check the dirty SCC cone) takes about 1-5 ms.
- NovyWave (435 KB, 11.9k lines, 17.7k parsed expressions): parse 4-8 ms, check 10-30 ms, lower+plan 15-40 ms. Diagnostics is about 15-40 ms and verified about 30-90 ms.
- Hashing in that design is one xxh3 pass over the sources (well under 0.1 ms), plus an optional SHA of the final plan only on export (a few ms).
These are estimates from node counts and per-node costs of well-engineered compilers, not measurements.
