## subsystem
Process, constraints and history governing compiler architecture (AGENTS.md compiler rules, budgets/compiler.toml, the performance contract, the plan documents, oracles, and the measurement protocol)
## purpose_summary
This area is the set of rules that decides which compiler changes are allowed to land. AGENTS.md has one compiler paragraph. It requires interleaved A/B/A 3+30 runs in both lanes and both cold modes, with the KernelRequirementWork counters, forbids editing budgets/compiler.toml, and bans reopening "linked transfer code or summary memoization". budgets/compiler.toml is the only executable budget and oracle. It freezes the build profile (lto=false, codegen-units=16, generic CPU) and the protocol (compiler_threads=1, compiler_caches=disabled, two cold modes, a product lane and an allocation-evidence lane). It also pins a machine_plan_sha256 per fixture, which is the SHA-256 of a 20 MB pretty-JSON export of the plan. BOON_COMPILER_PERFORMANCE_PLAN.md is the normative contract. It requires every verified compile to go through the full proof and receipt spine, says cold single-threaded cache-free compilation is normative, says a sampling profiler is optional, and closes only after three independent adversarial reviews. On top of that sit 12 BOON_COMPILER_* plan documents (13,281 lines) and 44 evidence JSON files (648 KB), several of which still call themselves active. The history runs as follows. Compiler performance work formally started on 2026-08-02. August went to representation packing: about 150 checkpoint commits that cut NovyWave allocations by about 45% but time by only 2-10%. From 09-07 to 09-14 came K0/K1/K1'/K1''. K1 made latency worse by 29-82%. Its machinery stayed in the tree under the scope rules, and K1'' then spent about 13 slices getting back to roughly where K0 was. From 09-27 to 09-28 came the M-plan retirements and closures. On 09-28 came the first sampling profile ever taken, and on the same day two small patches (T0, T1a) cut TodoMVC diagnostics by about 55%. Almost all of the measurable progress came from the single day a profiler was used. The process mostly produced documentation: since 09-06 docs grew by 20,992 lines and crates by 5,983, and 39 of 74 commits were docs.
## essential_work
- A semantics-preservation oracle that does not depend on representation: normalized diagnostics equality over a corpus (all examples plus a negative/invalid corpus), and behavioural equivalence of the produced plan on scripted scenarios. crates/boon_behavior_harness already exists: 'Product-faithful retained behavior and persistence harness without a native window'.
- Determinism within one compiler version: the same input compiled twice gives the same bytes. Across versions this is only needed if persistence or distributed roles depend on it, which is a question for the owner.
- Attribution with a sampling profile of the release binary before any target is chosen. Phase timers and work counters can only corroborate.
- Latency metrics that match the product: the real playground request sequence (EditorDiagnostics then VerifiedPreview), measured over a corpus of edit classes, plus cold first-open time.
- Guards against gaming: no fixture-specific code paths, no cache hits in a cold measurement, and scaling gates (doubling ratio) that catch super-linear blow-ups.
- Exhaustive verification wherever a plan crosses a trust boundary: decoding artifacts, loading from disk or network, deploying to console/FPGA.
- Continuous regression detection: a nightly full matrix on a quiet machine, plus a fast A/B loop sized to the effect being measured for development.
- One authoritative plan and one contract, with dated status.

## from_scratch_design
If this were set up from scratch with speed as the goal, the process would look like this.

(1) Governance. One COMPILER.md contract of at most about 300 lines covering product metrics, correctness oracles and how to measure, plus one living plan with dated status. Everything else moves to docs/archive; git keeps the history. The compiler section of AGENTS.md shrinks to about 8 lines of principles: profile before choosing; preserve semantics as the oracle defines it; never loosen a time budget; delete superseded code, and revert rejected experiments within the same goal; no fixture-specific code. Every 'do not' is written as a dated lesson with the tree hash, the measurement, and the condition under which it can be reopened. Technique classes such as memoization, linked code or a second solver are never permanently banned.

(2) Correctness oracles, layered.
- a: normalized diagnostics sets (code, span, message key) over all examples plus a negative corpus.
- b: behavioural differential: run old and new plans through boon_behavior_harness scenarios and compare output traces and persisted state.
- c: plan equality after canonicalization (IDs renumbered to a canonical order), used as the no-change check for pure refactors.
- d: exhaustive verify_plan and the IR checks in debug, test and CI builds, and at every decode or trust boundary.
- e: during an engine migration, a generated-program differential between old and new engines.
Byte hashes are used only for determinism (same build, same input, twice). The implementer updates oracle values in the same commit once a–c pass; only loosening a time or RSS budget needs the owner.

(3) Measurement.
- samply sampling of the release binary, with perf_event_paranoid=1 made persistent by the owner, is mandatory attribution.
- Counters and phase timers corroborate.
- Development uses a sequential A/B tool: interleaved, product lane only, fresh-process only, stopping on significance.
- A nightly CI job runs the full matrix, the warm edit corpus and the scaling gates on a quiet machine, and ratchets budgets down automatically when they are beaten by a margin.
- Report compiler_cpu_ms (already emitted) next to wall time, so threads cannot hide duplicated work while wall-clock parallelism is still allowed.

(4) Metrics.
- Primary: edit-to-preview p95 and edit-to-diagnostics p95 over an edit corpus of about 10 classes on TodoMVC and NovyWave, measured on the real EditorDiagnostics then VerifiedPreview sequence. Classes: literal change, rename local, add or remove a record field, add a function, introduce and fix a type error, incomplete syntax, cross-unit edit.
- Secondary: cold open-to-first-preview (threads allowed; a cache-assisted variant reported separately).
- Tertiary: single-thread cold throughput (lines/s) and doubling-ratio scaling gates, including call-path amplification.
- RSS as a delta over an empty-process baseline.

(5) Architectural freedom written into the contract. A clean-room engine may run alongside the old one behind a flag with a differential oracle and a deletion deadline. Build-profile changes (LTO, codegen-units=1, PGO, target-cpu) are ordinary A/B experiments. Proofs are built only when WHERE obligations exist. Self-verification runs off the critical path, or only at trust boundaries. Warm retention can land in stages: a whole-revision memo first, per-definition later. The compiler then targets a fast batch pipeline first: arena AST, per-definition inference over SCCs, direct lowering. Incremental bookkeeping (receipts, epochs, request graphs) is added only where the fast batch path misses the warm budget.
## speed_ceiling
All figures are estimates. They assume the clean design and process above: a batch compiler at about 1M lines/s parsing and 100-300k lines/s checking, with lowering of similar order, and no in-process self-verification on the preview path.
- TodoMVC (3.6k lines, 105 KB): parse 1-4 ms, check 12-36 ms, lowering/plan 5-20 ms. Cold diagnostics about 15-40 ms, cold verified about 30-80 ms. Today: 382 and 777 ms.
- NovyWave (12k lines, 435 KB): parse 4-12 ms, check 40-120 ms, lowering 20-60 ms. Cold diagnostics about 50-130 ms, cold verified about 80-200 ms single-threaded, and roughly half that wall-clock with per-unit and per-SCC parallelism on 8 cores. Today: 520 and 1906 ms.
- Warm, with definition-level retention: diagnostics 1-10 ms, preview 10-40 ms. Today: 379 and 1159 ms.
Parse today runs at about 188-198k lines/s (NovyWave 11,997 lines in 63.7 ms; TodoMVC 3,647 lines in 18.4 ms), about 5x below the reference. Checking runs at 9.9k lines/s (TodoMVC) and 26k lines/s (NovyWave), 4-30x below it.

Process changes alone make no code faster, but the evidence says they are what unlocked the gains. The one profiled day found a 36%-inclusive hotspot and a 15.8%-self hotspot that two months of timer and counter attribution had missed. Removing the proof spine from the preview path saves about 20% of NovyWave verified by the trace. Retention closes most of the warm gap. Under the current rules the realistic plateau is about what PROFILE_DRIVEN section 4 predicts: TodoMVC verified about 450 ms, NovyWave verified about 1000 ms, and cold budgets still out of reach. That plateau is set by the rules (no second solver, mandatory spine, bans on the summary path), not by physics.

## representation_critique
- structure: Plan identity oracle = SHA-256 of the pretty-JSON serde export | critique: It couples correctness gating to serde field names, ID numbering and formatting, so every internal representation improvement becomes a migration. It costs about 100 ms per verified sample, and it is already stale on two of three fixtures. | better: Canonical structural equality (IDs renumbered by a canonical traversal) plus behavioural traces. Hash canonical binary bytes only for determinism.
- structure: Receipts, seals and domain-separated CBOR+SHA-256 digests as first-class compiler data at every phase | critique: They are incremental and proof bookkeeping built before a fast batch compiler existed. The contract makes them non-removable ('would break the artifact digest contract'). They are about 40% of NovyWave's semantic phase, and there are zero WHERE obligations to prove. | better: A plain fast batch pipeline. Add structural fingerprints per definition only where warm retention needs them, and proofs only when obligations exist.
- structure: Type identity that includes authored field order | critique: It is mandated by the TENS plan and forces the order-receipt machinery through the requirement solver. | better: Order-free record types, with authored order in a per-definition side table read at persistence and render boundaries.
- structure: Plan documents written as agent /goal prompts with 'two honest endings' | critique: This makes the unit of work a bounded, auditable episode. It forbids crossing into 'successor' scopes (warm retention stayed a successor from 08-02 to now) and rewards writing evidence records over re-architecting. | better: One plan whose tiers may be re-ordered on profile evidence, and goals that may delete or revert anything they measure as net-negative.
- structure: Work counters as the attribution substrate | critique: Counters only count what someone chose to instrument. The 36% predicate had none, 18 production counters are structurally zero, and allocation counts fell 45% while time fell only 2-10%. | better: A sampling profile first, with counters added only to confirm a mechanism the profile already points to.
