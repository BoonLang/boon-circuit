## key
language
## subsystem
Language requirements the compiler must implement (static semantics of Boon), judged for inherent vs incidental compile cost
## purpose_summary
The docs ask for an annotation-free structural type system. It covers exact rational NUMBER, TEXT, BYTES (fixed [N] or dynamic), BITS[N], singleton Tags and tagged payloads, open records with width subtyping, and LIST/SET/MAP. It adds flow modes (continuous / tick-present / absent) for SOURCE/THEN/WHEN/WHILE/LATEST/HOLD, an implicit PASS/PASSED context, contextual OUT parameters, order-independent bindings that reject instantaneous cycles, no recursion, render-slot contracts, an order-chain typestate for sort_by/then_by, and Client/Session/Server adjacency (LANGUAGE_SEMANTICS.md; TYPE_INFERENCE_AND_TYPECHECKING_PLAN.md:95-214; OUT plan:515-660).

The docs never define two things that decide compiler cost: (a) the type of a join of heterogeneous branches, and (b) whether a statically known tag argument changes typing. The kernel defines both itself. For (b) it solves per call path and narrows results on singleton selectors: probe t1 (get(request: B) passed to a function needing .x) is REJECTED, while probe t2 (the same call with a dynamic HOLD selector) is ACCEPTED. For (a) it uses a field-union 'structural_widen': [a] joined with [b] becomes [a, b], and different kinds fall back to an open-object top (term.rs:1580-1682, solver.rs:2016-2034).

Probes on the release binary show the current checker enforces far less than the spec. These pass with 0 diagnostics and produce a MachinePlan: TEXT{x} |> Bool/not(), 5 |> Text/trim(), TEXT{x} - 1, [a:1] |> Text/trim(), 5 |> THEN{6}, LATEST over NUMBER vs TEXT branches, NUMBER|TEXT piped to Text/trim(), and an unused ordinary parameter. Some cases fail only later, with internal semantic/storage errors instead of diagnostics: recursion, the self-referential field [title: title], a missing PASSED field, a non-exhaustive WHEN, and reading a missing field on a closed record.

So the 364-443 ms TodoMVC typecheck mostly buys field requirements on user-function parameters, PASS presence, order chains, and exact per-instance shapes that the backend needs for typed storage. It mostly does not buy classic type safety.

Authored record field order cannot be observed at runtime: the canonical boon_data Value::Object is a BTreeMap<String, Value> (boon_data/src/lib.rs:229). It is still part of kernel type identity (term.rs:3086-3118 asserts [z,a] != [a,z]).

The spec itself asks for 'polymorphic contextual signatures ... instantiated at call sites' and 'one typed definition plus explicit call edges; it does not recursively clone the complete body at every call site' (OUT plan:866, 908-921). On TodoMVC the kernel instead compiles 10,537 call sites from 352 checked calls, and runs 416,698 summary-node evaluations for 4,079 checked expressions.
## essential_work
- Order-independent name resolution: collect all declarations in each scope (functions, modules, BLOCK variables, record fields, fresh OUT names), then resolve references. A local declaration shadows the outer one throughout its scope, and the registered roots (List, Element, Client...) cannot be shadowed. Textbook: two-pass symbol tables. O(n). Not expensive.
- Declaration dependency graph with cycle rules. Instantaneous cycles are rejected; a cycle is legal only through HOLD, SOURCE, publication or effect completion (LANGUAGE_SEMANTICS.md:216-222, OUT plan:497-513). Textbook: Tarjan SCC over edges labelled instantaneous/temporal. O(V+E). Not expensive.
- Call discipline: exact named entries in declaration order, bare entries only for OUT formals, a pipe fills the first ordinary parameter, and PASS is at most once and last. Unknown, missing, duplicate or out-of-order entries are errors (LANGUAGE_SEMANTICS.md:104-196). O(args) per call.
- No recursion in v1 (TYPE_INFERENCE plan:283-284, OUT plan:549-551), so the function call graph is a DAG. This is the most valuable compile-cost property Boon has: it permits bottom-up, once-per-definition inference with no polymorphic recursion and no SCC fixpoints among functions.
- Structural records: open width subtyping, HasField requirements flowing from callee bodies to call sites (probe p1 produces exactly this diagnostic), spread with ordered override precedence, and rejection of recursive shapes. Textbook: Rémy-style extensible rows with presence flags (or simple-sub bounds), near-linear with union-find. Only inherently hard case: spreading two OPEN rows ([...x, ...y] with both unknown) makes principal typing NP-hard (Wand 1989). Boon examples spread only call results or local closed records (grep: 57x ...NovyTheme/font, 10x ...Theme/material), so defer such spreads until they are closed.
- Tags and tagged payloads: singleton Tags (True/False are ordinary tags), closed and open tag sets, Tag[field] payload binding, and exhaustiveness without `__`. Textbook: OCaml polymorphic variants with lower/upper bounds. Singleton tags are standard, not exotic. O(arms) per WHEN.
- Heterogeneous branch joins are REQUIRED by the examples: Theme colors are `PASSED.mode |> WHEN { Light => Oklch[...], Dark => TEXT {...} }` (Theme/Classic.bn:22-65), and LIST literals mix element kinds. The spec never defines this join. A clean answer is a kind-partitioned union (at most one member per kind: TEXT, NUMBER, one record, one tag set, ...) whose record member merges with a presence lattice (Required vs Maybe). That is an O(#kinds) join, associative/commutative/idempotent, so the fixpoint is unique and order-independent.
- LIST<T>/SET<T>/MAP<K,V>: element join, MAP/SET key eligibility, collection-in-HOLD rejection and authority/ownership (foundations:1153-1343). Textbook: parametric types plus a type-directed occurs-style check after inference. O(type size).
- Flow modes: continuous / tick-present / absent, with rules per construct (TYPE_INFERENCE plan:163-188): THEN rejects a continuous input, HOLD needs a continuous init plus present updates, a pure call is the join of its arguments' flows. Textbook: effect/modality annotations over a 3-point lattice, with flow variables in schemes and join constraints. Near-linear. Today `5 |> THEN {6}` is accepted (probe r3), so this rule is specified but not enforced.
- SOURCE payload inference from where the source is bound (element kind decides .text/.key/...) and from the element.hovered/ElementState context. Textbook: SOURCE introduces a monomorphic, non-generalizable type variable (value restriction). Instantiating the consumer's scheme unifies it, so 'late providers' and 'backflow' need nothing beyond order-independent unification.
- OUT parameters: an argument that uses a fresh OUT is a rank-1 lambda over that OUT. Plus a per-definition scope-effect summary (which parameters are evaluated under which OUT) and an OutNet with exactly one producer and no alias cycles (OUT plan:515-600). Textbook: an HM function type plus a syntactic dataflow summary per body. O(size). The spec already says this summary is part of the signature and is 'instantiated at call sites' (OUT plan:801-809).
- PASS/PASSED: compile-time implicit context, where a root call must provide every field any transitive callee reads (PASS_PASSED doc:25-50). Textbook: an implicit row-typed parameter, like Haskell ImplicitParams or coeffects, carried in each function's scheme as an open-row requirement and composed bottom-up over the DAG. Today a missing PASSED field is not a type diagnostic (probe s3 fails in storage representation), although a missing PASS clause is (probe s1).
- HOLD, LATEST, WHEN, WHILE: HOLD init and update types must be compatible, LATEST joins its branches, WHEN joins its arms and checks exhaustiveness, WHILE needs a continuous selector. All linear. Runtime rules (LATEST event-sequence tie errors, PRIORITY/EXCLUSIVE) are not compile-time type work.
- Exact NUMBER: parse literals into normalized rationals once (LANGUAGE_SEMANTICS.md:49-54), with a small-integer fast path. Static range checks are a compile error when the value is known: round quantum <= 0, page size outside 1..=10000, BYTES/BITS positions and widths, Number/to_text options. Textbook: constant folding over exact rationals. Cheap if done as constant propagation. Expensive only if 'statically known' must be tracked per call path (the kernel carries static_number per evaluated value, owner_body.rs:4428-4434).
- BYTES[N] / BITS[N]: sizes are part of types, with width arithmetic (concat gives N+M, add_widening gives N+1) and fixed lengths refined from static TEXT literals (BYTES_SEMANTICS.md:93-107). Textbook: type-level naturals. Generalizing over widths inside user functions gives linear-arithmetic constraints (Cryptol-style). Simplest is to specialize BITS-using functions on concrete widths (HDL elaboration). Neither TodoMVC nor NovyWave appears to use BITS, so it is not on the hot path.
- Order-chain typestate: then_by needs a compatible preceding sort_by; filter, one-to-one map and take preserve the chain; others clear it (LANGUAGE_SEMANTICS.md:645-651). Enforced today (probe s5). Textbook: a lattice-valued attribute on LIST types with attribute variables in schemes. O(1) per operator.
- Render-slot contracts: root/items/child slots checked structurally against a registry (BOON_TYPE_NOTATION:80-110). Textbook: subtyping of a record against a closed contract, O(fields).
- Distributed roles: only adjacent Client-Session-Server edges, qualified names, SessionInfo availability per role (LANGUAGE_SEMANTICS.md:247-309). Per-declaration role tags plus an edge check. O(E).
- FLUSH: private fail-fast control that becomes union data at FUNCTION, BLOCK-final or root boundaries (BUILD.bn header). Textbook: an exception/effect row turned into a result union at the boundary, like Koka effects. Linear.
- Diagnostics: source-span based, Boon vocabulary, and a cycle diagnostic that shows the declarations and edges involved. Cheap if every constraint carries a span id and error text is rendered lazily from one solve.
- Needed only for execution (verified path): a state/source instance per call path and row scope (OwnerInstanceId, OUT plan:662-700), a dependency graph for dirty propagation, typed storage layout, list access plans, and deterministic IDs. This is essential output. It is a memoized tree walk over (definition, static args, concrete arg types), not a type-inference problem.

- problem: The WHEN/LATEST branch join is not monotone and depends on solve state, which forces retraction plus receipts to stay deterministic. | evidence: solver.rs:2016-2034: if any candidate has_variable the result is union(candidates), otherwise a structural_widen fold. The whole solve becomes near-linear, O(N alpha(N)), with no retraction.
- problem: The field-union widen is unsound and falls back to an untyped top, while the static case is typed precisely, so making a value MORE dynamic makes a program MORE accepted. | evidence: term.rs:1660-1676: record join keeps the union of fields (a field in one arm becomes present in all). term.rs:1682: any other kind mismatch becomes an open empty object. - problem: Parameter requirements are principal (all arms) while results are narrowed per path, so each definition is typed twice under different rules. | evidence: Probe p1: with a static kind A, the unselected arm B still demands data.count ('argument data is missing field count'). ## from_scratch_design
ANSWERS TO THE SPEC QUESTIONS

(4a) Authored field order is NOT semantically observable, going by the docs and the runtime. LANGUAGE_SEMANTICS.md:8-16 defines structural data equality. Foundations:1197-1212 orders closed objects 'by canonical field-name order' for enumeration, hashing and serialization. The persistence plan uses canonical field order. The runtime value is Value::Object(BTreeMap<String, Value>) (boon_data/src/lib.rs:229).

Order does matter in three places, none of which needs it in type identity:
- Spread override precedence (spread vs explicit field position decides which value wins). This is value-level and resolved when the record is built.
- Presentation: hint and diagnostic examples print fields in authored order.
- Byte-pinned oracles: machine_plan_sha256 in budgets/compiler.toml:43/53/63 and diagnostics_fingerprint_v1. The plan JSON keeps authored order, e.g. probe u1 emits fields [b, a].

Only the compiler plans (TENS_OF_MILLISECONDS_ARCHITECTURE_PLAN:115, GOAL_PROMPT:85) require 'exact object field order'. That is a parity rule, not language.

(4b) The docs describe per-definition schemes: 'polymorphic contextual signatures' in CheckedProgram (OUT plan:866), 'scope-effect summary ... instantiated at call sites' (OUT plan:801-809), and 'one typed definition plus explicit call edges ... does not recursively clone the complete body at every call site' (OUT plan:908-921). Recursion is rejected. For every compositional rule (rows, variants, flows, PASSED rows, OUT lambdas, order chains), per-definition principal schemes therefore accept exactly what per-call inlining would accept (the standard let-polymorphism equivalence).

The one real non-equivalence is the de facto rule that a statically known tag selects a WHEN arm and narrows the call's result type (t1 rejected vs t2 accepted; Element/stripe 'narrowed to Row or Stack when the direction value is known', BOON_TYPE_NOTATION:217). The examples depend on it for PRECISE shapes: Theme/get with request tags returns NUMBER for Sizing and records for Material/Font. The current checker is lenient enough that dropping it would mostly lose backend storage precision rather than change acceptance. That rule is not in LANGUAGE_SEMANTICS.md, so the owner has to decide it.

(4c) Exact-value / literal types:
- Tags are singleton types. This is standard polymorphic-variant inference, not exotic.
- The non-standard parts are value-dependent: static_number tracking for compile-time range checks, BYTES[N] refined from literal TEXT, BITS width arithmetic, and result narrowing on singleton selectors through calls.
- All of these are 'static value' facts, better handled by constant propagation / binding-time analysis than inside the unifier.

CLEAN DESIGN (types and front half)

1. Front end
- Per-unit lexing and parsing into an arena AST with u32 spans and interned SymbolIds.
- Order-independent resolution: collect declarations, then resolve.
- One declaration graph with labelled edges. Tarjan SCC rejects instantaneous cycles, recursion (any function SCC larger than one, or a self-edge) and self-referential fields, each with a real diagnostic.

2. Binding-time analysis (BTA) and specialization
Only needed if the owner keeps static-selector typing.
- Walk the function DAG bottom-up and mark which parameters feed a WHEN selector, a BITS width, or a static-checked NUMBER position.
- At each call, compute the static projection of the arguments: literal tags, numbers and text, static tag payloads, static PASS fields.
- Memoize one specialized body per (definition, static tuple) in a hash-consed table.
- Unselected arms are dropped before typing, so requirements and results follow one consistent rule. That removes syntax_selected provenance and hole erasure.
- Cost is linear in total specialized size. TodoMVC is estimated at 500-1,500 specializations of 5-40 nodes each.

3. Inference
Runs once per (specialized) definition, bottom-up over the DAG.
- HM with level-based generalization.
- Rémy-style rows with presence flags for records.
- OCaml-style polymorphic variants for tags and payloads.
- Kind-partitioned unions for heterogeneous joins.
- Lattice attributes with variables for flow mode (continuous / present / absent) and list order chain.
- An implicit PASSED row in every scheme.
- OUT-dependent arguments as rank-1 function types.
- Value restriction: SOURCE, HOLD and top-level values are monomorphic.

Functions that read globals (e.g. new_todo reading store.*, while store calls new_todo) are checked with the global's type as an outer-level variable. The function generalizes only over its own variables. This is sound because globals are monomorphic, and it breaks the store/function letrec without extra passes.

Builtins and render contracts come from a static, precompiled signature table (built once and shared, not rebuilt per compile). Complexity is near-linear, O(N alpha(N)), plus the sum over calls of scheme size.

Because everything is monotone and confluent, the output is deterministic by construction: IDs are assigned in DAG and source order and types are printed canonically. No receipts are needed.

4. Diagnostics
One solve, one pass. Each constraint stores a span id and a small provenance tag, and error text is rendered lazily. Authored field order lives in a per-record-literal side table used only for display. There is no RuntimePacked-versus-EditorRich second solve.

5. Incrementality
The reuse key is (definition content hash, static tuple, hashes of callee schemes). This is sound because a scheme is a pure function of those inputs (unlike the kernel's requirement results). A type-preserving edit re-parses one unit, re-infers the touched definitions, finds their schemes unchanged, and stops.

6. Verified path
Monomorphize by (specialization, concrete argument types) with memoization, so the M3 data suggests roughly a 20x collapse. Emit typed storage layouts and dependency graphs directly into the plan builder. Certify and verify_plan only at load and trust boundaries.

EXPECTED CHECKING COMPLEXITY
Linear in source plus specializations. There are no exponential paths apart from pathological static-argument combinatorics, which are bounded because recursion is absent. Add a hard cap with a diagnostic.
## speed_ceiling
All numbers are estimates from measured node counts, not measurements.

TodoMVC (105 KB, 4,081 checked expressions, 352 checked calls, 4,536 semantic nodes):
- Parse 2-4 ms (at 30-50 MB/s lexing plus a linear parse; today 18.6-21.3 ms).
- Resolve and SCC about 1 ms.
- BTA/specialization 1-3 ms (500-1,500 specializations x about 20 nodes).
- Inference 3-8 ms (about 100k union-find/row operations at 20-80 ns).
- Diagnostics cold total about 8-15 ms, against a 75 ms budget and 364-388 ms today.
- Warm type-preserving edit about 1-4 ms (one unit re-parse plus one definition re-infer, scheme unchanged), against a 16.7 ms budget.
- Verified adds monomorphized lowering and plan emission, about 10-30 ms, for a total of about 25-50 ms against a 300 ms budget and 810 ms today.

NovyWave (435 KB, 15,650 checked expressions, 1,821 checked calls, 16,340 semantic nodes):
- Parse 8-15 ms (today 64-92 ms).
- Inference 10-25 ms.
- Diagnostics about 20-40 ms, against a 250 ms budget and 526-573 ms today.
- Verified about 60-120 ms, against a 1,000 ms budget and 1,870-1,891 ms today.

Reasoning: today's typecheck costs 30-89 us per checked expression and semantic costs 36-47 us per semantic node. Production HM-family checkers spend about 0.1-1 us per node. The gap is explained by about 100 summary-node evaluations and about 65 term-intern requests per expression, which come from per-call-path solving, non-monotone joins with retraction, and in-process certification. None of these is required by the language.

## questions_for_owner
- question: Is authored record field order (and authored tag-union order) ever semantically observable, or only a presentation detail for hints and diagnostics? | why_it_matters: If it is presentation only, type identity becomes order-free: hash-consed canonical shapes, no order receipts, no variant_set_preserving_order. That is: unselected WHEN arms impose nothing, and the call's result narrows to the selected arm (Theme/get(request: Sizing[...]) returns NUMBER; t1 rejected while t2 is accepted).
