## subsystem
Product integration and warm path: CompilerSession / KernelSession / native playground compile worker / distributed + migration + child-program compile paths / compiler-sample + verify-compiler-interactions harness
## purpose_summary
What runs when you type one character in the playground. (1) The dev process marks the edit as EditorText, bumps its revision, clones every source unit and sends DevSourceChanged over bincode IPC (dev.rs:350-358). (2) The desktop supervisor stores the units and re-sends the whole bundle to the preview as PreviewApply (desktop.rs:189-203, 367-396). (3) The preview event loop hashes the bundle (preview_project_key, preview.rs:1252) and calls CompileWorker::replace (preview.rs:1312). That call cancels a token and wakes the single thread "boon-preview-compile" (compile.rs:127-160). (4) On that thread, PreviewCompiler::compile_built_in diffs the unit strings, calls CompilerSession::apply_updates and bumps the revision. apply_updates sets diagnostics=None and checked=None (session.rs:485-486). (5) request(EditorDiagnostics) re-parses only the edited unit (parse and link requests are the only retained, incremental state). It then runs a full, from-scratch EditorRich check: source ABI, prepare_kernel_project_projection, KernelProjectInput, KernelSession::new, the CheckedImage solve, rows, the parity oracle and rich metadata (session.rs:753-764, kernel_oracle.rs:2837-3181). After that it builds the editor language projection. (6) request(VerifiedPreview) consumes that checked result through state.checked.take() and runs Rich semantic, IR, backend and verify_plan (session.rs:766-811). (7) Only then does the worker send one CompileOutcome carrying both the language snapshot and the plan (compile.rs:373-393), so the editor sees diagnostics only after the whole verified compile (preview.rs:1500-1508). A separate readiness thread then prepares the runtime swap. Per keystroke that is 1 full typecheck plus 1 full back half. No typecheck, semantic or backend state is retained, because KernelSession is created and dropped inside kernel_oracle.rs:2891. Cancellation is only polled between phases (8 checkpoints per compile), so a superseded keystroke still runs its ~365-445 ms solve to completion. Migration examples open a new CompilerSession for every stage on every keystroke (compile.rs:744-811, 848). Distributed packages run the legacy boon_typecheck in a fixed-point loop with at least 12 full role checks and no session (distributed_compiler.rs:1008-1034, 1258-1268, 1432-1450). The CLI warm benchmark measures a different sequence: Diagnostics, then VerifiedPreview, which type-checks twice. The interactions gate hard-codes a Fail status.
## essential_work
- Accept an edit and map it to changed source units and changed top-level definitions.
- Re-parse at most the edited top-level item (or unit), keeping stable definition identity across revisions.
- Re-resolve names for changed definitions and update the definition-level dependency graph and its SCCs.
- Re-infer the types of changed definitions/SCCs, compare their published interface fingerprints with the previous revision, and propagate only when an interface changed (early cutoff).
- Publish diagnostics for the new revision; rebase spans for definitions that only moved.
- Build the verified MachinePlan for the new revision (at least the changed fragments) and hand it to the runtime, keeping the last good plan on failure.
- Supersede stale revisions with bounded stop latency (latest-wins).
- Keep enough retained state (interfaces, per-definition facts, per-definition lowering) that the next edit can do all of the above.

- problem: Migration preview is O(stages * project) per keystroke. | evidence: compile.rs:757-809 with a fresh CompilerSession per stage (compile.rs:848). | fix: Cache predecessor MigrationPredecessorBinding plans by stage source digest; retain one session per stage. | complexity: O(stages) full compiles per keystroke; target O(1).

## from_scratch_design
A warm-first compiler service with one immutable snapshot per revision, a query graph at definition granularity, and two publication lanes.

1) Input and transport. The editor sends deltas (unit, byte range, new text, revision), not whole bundles (today dev.rs:354 and desktop.rs:372 clone every unit per keystroke). The compiler keeps each unit as a rope plus a cached digest. The bundle digest is a Merkle combination of unit digests, so each keystroke hashes only the changed unit (today it is at least 7 full SHA-256 passes).

2) Syntax. The unit of reuse is the top-level item. A keystroke re-lexes and re-parses only the enclosing item, falling back to the unit when item boundaries change. Each item gets a StableItemKey (unit + route, which already exists as StableOwnerKey) and a SyntaxHash over its normalized token stream with positions relative to the item start. Moving an item down a line therefore changes nothing but a line offset applied at presentation (the code already has rebase_definition_spans).

3) Identity. A single interner retained across revisions (append-only, never renumbered) gives stable SymbolId/PathId values. Definitions are addressed by StableItemKey; dense indices are per-revision locals and never part of a reuse key.

4) Resolution and graph. Each item gets a free-name set, which yields def-to-def edges. SCCs are recomputed incrementally, or fully: 155 to ~1k nodes takes microseconds.

5) Checking. Each SCC gets a query Check(scc) whose input key is (SyntaxHash of its members, InterfaceFingerprint of each direct dependency). Its output is an Interface (the value type or function summary that callers see), its InterfaceFingerprint, the definition's per-expression facts (types for hover), and diagnostics, all position-relative. When the key matches, reuse the output. When the SCC is recomputed and the InterfaceFingerprint comes out equal, backdate it, so dependents' keys do not change (Salsa early cutoff; this needs the AGENTS.md reuse-key rule clarified). Functions are summarized once per definition and instantiated at call sites. Callee bodies are not re-solved per call path (today 352 calls become 10,537 frames).

6) Diagnostics lane. Diagnostics are the union of per-definition lists and are published as soon as the check queries settle, before any lowering. Presentation is O(changed definitions); the language snapshot to the editor is a delta.

7) Preview lane, on a separate worker. It reads the same Arc snapshot, lowers per definition (keyed on the check output fingerprint plus the lowering-relevant dependency interfaces), links fragments into a MachinePlan with ids derived from stable keys, and hands the runtime a plan delta. The runtime already supports same-identity replacement builds (readiness.rs prepare_machine_plan_build). Full verify_plan runs only for plans loaded from outside; in-process fragments are trusted, with debug-assert checks. The last good plan stays live until a newer revision succeeds (already done: session.rs:487-490).

8) Scheduling and cancellation. There is a generation counter; the solver polls it every N operations and lowering polls it per definition, giving stop latency around 1 ms. A new edit cancels the preview lane immediately; the diagnostics lane is short enough to just finish.

9) Parallelism. Cold: parse units in parallel (9 NovyWave units, 8 TodoMVC), then check SCCs level by level in a work-stealing pool, then lower definitions in parallel. Warm: a single thread is enough for diagnostics; the win from threads there is pipelining the two lanes.

10) Memory. Retained state is per-definition interfaces, facts and lowered fragments, so memory stays proportional to program size, not call paths. Solver scratch is per SCC and freed after it settles.

11) Distributed and migration become clients of the same query graph. Cross-role interface slots are just more inputs, and predecessor migration stages are cached queries keyed by stage digest.
## speed_ceiling
All figures below are estimates for the clean design unless marked measured.

Warm, type-preserving edit (the budget's literal edit), same on TodoMVC and NovyWave because the work does not scale with project size:
- item re-parse ~0.1-0.5 ms (today a whole-unit re-parse measures 6 ms on TodoMVC and 42-49 ms on NovyWave);
- recheck of one definition, with the cutoff on its unchanged interface, ~0.2-1 ms;
- diagnostics and language delta ~0.5-2 ms, plus IPC ~0.5 ms.
- Total edit-to-diagnostics ~2-5 ms, against a 16.7 ms budget and today's measured 371-385 ms (TodoMVC) and 525-586 ms (NovyWave) in the CLI, or ~800 ms+ / ~1.9 s+ in the product, where diagnostics wait for the verified compile.

Type-changing edit (interface change used by a cone of k definitions): O(k) rechecks. For k = 10-40 that is roughly 3-15 ms.

Warm verified preview: re-lower changed definitions and relink or patch the plan, ~5-20 ms, against a 100 ms budget and today's measured 1145-1164 ms (TodoMVC) and 2404-2588 ms (NovyWave).

Cold, single-threaded:
- TodoMVC (3.6k lines): parse ~3-5 ms, check ~20-40 ms, lowering and plan ~15-30 ms; about 40-75 ms verified.
- NovyWave (12k lines): parse ~12 ms, check ~60-120 ms, lowering ~40-80 ms; about 110-210 ms verified.
- With 8 cores and SCC-level parallelism, NovyWave cold check drops to roughly 25-50 ms.

Why today is 10-100x away on the warm path: nothing after parse is retained (KernelSession is dropped per request); the key inputs (projection plus kernel input) alone cost a measured 30 ms and 132 ms; the check is whole-program with 20-30x call-path amplification; diagnostics are published only after the verified back half; and cancellation is polled only at phase boundaries.

## representation_critique
- structure: ProjectState result slots (diagnostics: Option<CompilerDiagnostics>, checked: Option<CheckedSourceFromSource>, compiled, request_graph) | critique: These are whole-program blobs invalidated wholesale on every edit (session.rs:485-486, 635-636). There are separate slots per intent, so Diagnostics and Verified never share a solve, and checked is consumed by take() (session.rs:787). The only fine-grained, typed request tables cover parse and link. | better: Per-definition query tables keyed by StableItemKey plus a content/interface fingerprint, with changed_at/verified_at epochs and backdating. Intents become different demand roots over the same tables. | evidence: session.rs:189-206, 731-816
- structure: CompilerSessionResult<'a> borrowing &'a mut CompilerSession | critique: A synchronous, single-caller API. Results borrow the session mutably, so a diagnostics lane and a preview lane cannot run at once, and one revision's snapshot cannot be handed to another thread. The collector notes it 'exposes no worker generation handle'. | better: An immutable Arc<RevisionSnapshot> per revision, with requests returning Arc-shared products, a generation token checked cooperatively, and a small scheduler owning the lanes. | evidence: session.rs:151-158, 711-717; compiler_interactions.rs:626
- structure: Global dense ids (KernelOwnerId, SymbolId, PathId, KernelTypeRef, TypeTermId) assigned fresh per compile in first-appearance order | critique: Any insertion renumbers later ids, so no product of one revision can be compared or reused in the next without remapping. That is why M4 saw 23% stability on a type-changing edit. Retained kernel state is structurally impossible while every request builds a new catalog. | better: A retained, append-only interner shared across revisions (existing ids never move). Cross-revision identity by stable content keys; dense indices only as per-revision locals. | evidence: kernel session.rs:26-116 (a fresh PackedTextCatalogBuilder per KernelProjectInputBuilder); packed_owner.rs:39-99
- structure: owner_program_fingerprint (the planned T5 reuse key) | critique: It hashes only node kinds and modes, leaving out the edge column and input spans, and the kinds embed dense ids. It gives false 'unchanged' results for rewired inputs (unsafe) and false 'changed' results when ids shift (useless). Computing it requires the full O(project) projection anyway. | better: A per-item SyntaxHash over normalized tokens (position-relative) computed from syntax, plus an InterfaceFingerprint over the solved interface with stable-key symbol names. | evidence: packed_owner.rs:181-236; measured projection+input 30/132 ms
- structure: CompileOutcome { language, result } as a single message | critique: It couples the fast artifact (diagnostics) to the slow one (plan), so edit-to-diagnostics equals edit-to-verified. | better: Two messages per revision on independent lanes: LanguageSnapshot(rev) as soon as checking settles, then PlanReady(rev) or PlanFailed(rev). | evidence: compile.rs:60-68, 373-393
- structure: Keystroke transport: Vec<SourceUnit> full-bundle clones through dev, desktop and preview, re-hashed at each stage | critique: O(project) copying and hashing per keystroke: at least 7 SHA-256 passes over 206-435 KB, 2 IPC hops each way. It is small per hop but pure overhead against a 16.7 ms budget. | better: Text deltas with revision numbers and per-unit cached digests combined as a Merkle hash. | evidence: dev.rs:354-358; desktop.rs:372-386; preview.rs:1252; compile.rs:416, 498; session.rs:851
- structure: Kernel per-call-path frames solved as one global worklist (ComponentSolver with a single pending VecDeque) | critique: State is proportional to call paths, not program size: 10,537 compiled call sites from 352 checked calls, and 82k variables for 4k expressions. There is no SCC decomposition to parallelize or retain per definition. Typecheck adds ~85-100 MB of RSS. | better: Per-definition principal summaries solved bottom-up over definition SCCs, with per-SCC scratch freed after settling and retained interfaces only. | evidence: solver.rs:280-299; measured kernel_compile.compiled_call_sites 10537, kernel_solve.variables 82358
