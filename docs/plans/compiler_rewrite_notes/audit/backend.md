## purpose_summary
After semantic elaboration, boon_verify::verify_explicit_contracts wraps the SemanticProgram in a proof token. This costs 0.05 ms. boon_ir::erase_and_lower does not actually lower anything. erase_semantic_program (boon_ir/src/lib.rs:297-326) moves CanonicalProgramCoreV2 out of the semantic program, drops the rest, binds the pulse-fusion decisions, and then runs three verifiers: verify_erased_scope_index, verify_static_schedule and verify_hidden_identity. So 'ir_lower' is verification plus freeing the semantic graph. finish_checked_program_to_machine_plan (boon_compiler/src/lib.rs:1411-1414) then runs verify_hidden_identity and verify_static_schedule a second time on the same immutable value. That is 'ir_validation'.

compile_erased_program_with_distributed_context (machine_plan_backend.rs:4825 onward) builds the MachinePlan in several phases: indexes/storage, derived values, state updates, list mutations, a document plan built by DocumentCompiler (document_executable_backend.rs), and finalize. Finalize clones the whole plan to refresh list-view fingerprints, re-interns every row expression during compaction, and re-validates reachability. CompiledMachinePlanFromSource::seal (lib.rs:531-545) calls boon_plan::seal_machine_plan, which runs verify_plan. verify_plan builds about 41 PlanCheck structs, each with a formatted String, and then calls plan_sha256. plan_sha256 serializes the entire plan through a self-describing serde encoder that writes every struct, newtype and enum name plus u64 lengths (binary.rs:224), then SHA-256s the bytes. This is 'plan_validation'.

On the runtime/playground path, artifact_from_compiled (program_core.rs:694) calls validate_plan (program_host.rs:300). validate_plan calls boon_plan::verify_plan again at program_host.rs:498. The path then CBOR-encodes the whole plan and SHA-256s those bytes twice (ContentArtifact::new, then validate_content_artifact, in boon_persistence lib.rs:772-780 and 2904). The distributed path verifies each role plan three times: distributed_compiler.rs:2913, program_core.rs:660 seal, and program_host.rs:498. It also clones the whole IR per role (distributed_compiler.rs:2557).

Measured today (ms): TodoMVC back half = ir 2.7+0.6, backend 86-90, plan_validation 91-94. NovyWave = ir 17.6+7.9, backend 221, plan_validation 66-69. On TodoMVC the back half alone (~180 ms) is 1.8x the whole 100 ms warm-preview budget.
## essential_work
- Assign runtime storage: scalar slots per state cell, list slots with row-field layouts, fixed-byte banks, and map each IR StateId/ListId/FieldId to a slot.
- Build the dataflow schedule: ops for source routes, derived values, state-update arms, list mutations and projections, plus dependency and dirty edges, pulse batches, activations and demand roots.
- Lower executable expressions into an evaluable form with shared subexpressions: row expressions for dataflow, and document/template expressions for the view.
- Build the document structure: templates, materializations, view bindings and the initial patch batch.
- Derive persistence identities that must stay stable across compiles (memory IDs, type fingerprints, migration catalog). A cryptographic hash over small canonical inputs is legitimate here. There are hundreds of items, not megabytes.
- Build effect contracts and outbox schemas.
- Produce a stable plan identity only when something consumes it (artifact caching, app packaging, the server comparing artifacts). It can be lazy.
- Fully validate plans that come from outside the process (decode_program_artifact, app bundles). In-process plans need no runtime re-proof.

## from_scratch_design
A trusted in-process back half should do one linear emission pass over a compact, already-monomorphized IR into flat, hash-consed arenas, with zero runtime self-verification.

(1) Input contract. The middle end hands over a typed IR with interned TypeId(u32), SymbolId(u32) and TypeEnvId(u32), and dense ids for fields, lists, states, bindings and statements. Per-entity attribute tables are built once while the IR is constructed: is_runtime_row_storage as a BitVec, fields_by_list_and_name: FxHashMap<(ListId, SymbolId), FieldId>, and parent_of_statement as a Vec. No type trees are cloned per expression. Polymorphic instantiation, if still needed, is memoized per (FunctionId, TypeEnvId).

(2) One expression DAG, not two. Row and document expressions share one arena: kind: Vec<u16>, a: Vec<u32>, b: Vec<u32>, extra_start: Vec<u32>, and extra: Vec<u32> for variable-arity operands. Operands carry a 1-bit tag for constant vs node, so there is no Constant node. Hash-consing uses FxHashMap<(kind, a, b, extra-slice fingerprint), ExprId> with equality on hit, and a node's 64-bit structural fingerprint is computed from its children's fingerprints when it is created (Merkle). Constants live in one pool interned by canonical bytes. Names use one SymbolId table. Provenance (compiler_id, debug labels, paths) goes in a side table that is neither hashed nor serialized for execution. On today's TodoMVC this collapses the document from 64,482 to about 10.9k nodes (conservative measurement) and removes 29,917 Constant nodes.

(3) Document specialization. Decide specialize, share or inline before emitting, from the static call graph (single-use call sites are known from the IR). Memoize each specialization by an interned Copy key (FunctionId, TypeEnvId, OverlayId). Emit function bodies once and reference them from call frames. There is no compile-then-inline pass, no per-call-site cache scope, and no CompileContext clones: use persistent or immutable maps, or a scoped undo log.

(4) Dataflow ops. Iterate derived values, update arms and mutations once. Resolve inputs through dense tables, not string paths. Emit only reachable nodes, driven from the roots, so there is no compaction or reachability pass. List-view and persistence fingerprints come from the node fingerprints already computed in (2).

(5) Identity. A plan identity is a lazily computed OnceLock over a Merkle root of per-arena chunk hashes: xxh3-128 for caches, blake3 when cryptographic strength is needed. Persisted artifacts use the single content hash of their serialized bytes, computed once. No name-bearing canonical encoding is ever hashed.

(6) Verification. Keep zero-cost type-state tokens (private constructors) as the in-process guarantee. Structural invariants go under debug_assertions. The full verify_plan with its 41 checks runs in a CI lane over all examples plus fuzzed and mutated plans, and always at the untrusted deserialization boundary (decode_program_artifact, app bundles, MachineTemplate::new). In-process release builds run zero verifiers.

(7) Serialization. Use one compact, versioned binary encoding without names (postcard or bincode-like, with a single format-version constant) for both storage and hashing. JSON is for debugging only.

(8) Memory. Use a per-compile bump arena for IR and semantic data, so drops are O(1): today about a third of NovyWave ir_lower is drop_glue.

(9) Incrementality. Keep stable per-owner ids so a warm edit re-emits only the affected owners' ops and expressions. The plan becomes a set of per-owner segments, and the Merkle identity updates incrementally.
## speed_ceiling
These are estimates, derived from measured node counts times roughly 100-200 ns per emitted or looked-up node (FxHash lookup, arena push, occasional small allocation).

TodoMVC has 4,536 executable expressions, about 11k document nodes after hash-consing (fewer with memoized specialization), 73 final row expressions, 126 fields and 28 update arms. Back half: IR erase ≈ 0.2-0.5 ms (a move plus an O(1) arena free), backend ≈ 3-5 ms, plan identity ≈ 0 (lazy) or ~0.2 ms (xxh3 over ~1 MB), in-process verification 0 ms. Total ≈ 4-6 ms, against ~180 ms measured today (2.7+0.6+86+91). That is 30-45x.

NovyWave has 16,340 executable expressions, 2,071 row expressions, about 7.6k document nodes (conservative), 1,433 fields, 591 bindings, 359 derived values and 878 update arms. Back half: IR ≈ 1-2 ms, backend ≈ 10-15 ms, identity ≈ 0.5 ms. Total ≈ 12-18 ms, against ~310 ms today (17.6+7.9+221+66). That is ~20x.

A warm single-owner edit with per-owner incremental emission should be about 1-2 ms of back half.

For comparison, production code generators emit well over 1M IR nodes/s per core. At that rate NovyWave's ~30k nodes of emission take tens of ms at worst and single-digit ms when done well.

The quick wins alone (listed separately) are estimated to take TodoMVC's back half from ~180 to ~60 ms and NovyWave's from ~310 to ~110 ms. That still consumes most of TodoMVC's 100 ms warm-preview budget, so the format and design change is required, not optional.

## representation_critique
- structure: DocumentPlan.expressions (boon_plan/src/document.rs:108-204) | critique: It is a tree of Rust structs with Vec fields per node, and it is never hash-consed. compiler_id (provenance) sits inside each node, so identical ops cannot share. A separate Constant node exists for every constant use: 29,917 of 64,482 TodoMVC nodes (46%). The conservative hash-consed size is 10,946 (5.9x smaller) on TodoMVC and 7,655 (4.1x) on NovyWave. Each Record, List or Call node costs at least one heap allocation. | better: A flat SoA arena (kind u16, a/b u32, operand pool u32) with tagged operands (constant vs node), hash-consed via FxHashMap. Provenance and debug labels go in a side table excluded from execution and hashing.
- structure: boon_plan::binary canonical encoding used for plan identity and for interning keys | critique: It is self-describing: every struct, newtype, enum and variant name is written as a u64-length string, and every length is u64 (binary.rs:224, newtype and unit-variant handlers). An id newtype costs ~38 bytes instead of 1-4. The TodoMVC encoding is estimated at ~30 MB, against 9.2 MB compact JSON and ~6.6 MB CBOR. It also ties every plan hash to Rust type and field names, so renaming a struct changes all digests. | better: A name-free, schema-versioned compact encoding (varint ids) with a single format-version constant, hashed lazily with xxh3/blake3. For warm reuse, per-arena Merkle chunk hashes.
- structure: PlanRowExpressionArena.structural_index: Option<BTreeMap<[u8;32], Vec<PlanRowExpressionId>>> (boon_plan lib.rs:8866-8870) | critique: It uses a cryptographic digest of the name-bearing encoding as a hash-table key. It is computed on every intern, including hits, rebuilt from scratch after deserialize (serde skip) or when absent, and cloned with the arena during trial lowering. | better: #[derive(Hash)] on nodes plus FxHashMap<node-hash, SmallVec<Id>> with equality on collision, or a node fingerprint computed at creation from children fingerprints.
- structure: Two expression languages and two lowerers (PlanRowExpressionNode via ExecutableRowLowerer; DocumentExprOp via DocumentCompiler), with separate constant pools (plan.constants vs document.constants) and interning disciplines (SHA-interned vs none) | critique: The same executable IR is lowered twice with different sharing rules, and the runtime needs two evaluators. Neither shares subexpressions with the other. | better: One expression DAG and one constant pool. Document and row evaluation become different interpretations or roots over the same arena.
- structure: ErasedProgram / CanonicalProgramCoreV2 (IR) | critique: flow_type holds a full boon_checked::Type inline per executable expression: 12.8 MB of NovyWave's 21.5 MB expression JSON. Scope bindings also carry full object types. Types still contain variables that the backend re-substitutes per call (apply_checked_type_environment). Paths and names are Strings used as lookup keys (derived.sources: Vec<String>, BTreeMap<(String,String),FieldId>, ValueRef::StateProjection{field_path: Vec<String>}). | better: Interned TypeId/TypeEnvId/SymbolId (u32), monomorphized before the backend, with dense per-entity attribute tables (row-storage flag, owner list, name symbol) built once.
- structure: MachinePlan partial-plan and derived fields: unresolved_executable_ref_count per PlanOp, capability_summary, dirty_plan/commit_plan counters, stored persistence hashes | critique: The target format can represent incomplete or unexecutable plans and stores derived counts and hashes, so verify_plan must recount, rehash and compare them (lib.rs:11476-11492). In-process that can only catch backend bugs. | better: Make incomplete plans unrepresentable: the backend returns Err rather than emitting unresolved ops. Derive summaries on demand, or keep them debug-only.
- structure: Backend maps: 127 BTreeMap, 0 HashMap and 107 linear `.find(|` in machine_plan_backend.rs; BTreeMap<String,…> caches in DocumentCompiler (name_ids, compiled_paths, pattern_bindings) | critique: Ordered maps and linear finds are used where ids are dense or order is irrelevant. String keys cost memcmp and allocation (for example 8491 allocates two Strings per lookup). | better: Vec indexed by dense id, FxHashMap for sparse keys, and a symbol table for names. Keep BTreeMap only where deterministic iteration order is part of the output, and sort once at emission instead.
