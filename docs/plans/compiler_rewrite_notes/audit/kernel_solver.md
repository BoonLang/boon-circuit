## subsystem

## purpose_summary
The kernel solver takes a single global ComponentProgram and runs it to quiescence. In that program every definition body has already been instantiated per call path into residual frames, direct operations and per-definition summary bytecode. In textbook terms it is not Hindley-Milner: it has no levels, no generalization and no schemes. It is not Simple-sub/biunification either, since it keeps no lower/upper bound lists. It is a chaotic-iteration dataflow worklist over hash-consed type terms, with three parts. (1) A union-find (rank plus recursive path compression, solver.rs:3567-3626) carries equality constraints. Bindings are merged with merge_type_evidence, which is open-record field union, not row unification. (2) Directional 'authoritative' transfer functions (Publish Union/StructuralWiden/Replace, Select, Record, Collection, Projection, SummaryCall) replace their output's binding. They are non-monotone: select() at solver.rs:1976 joins every arm while the selector is unknown or has several tags, then keeps only the first accepting arm once the selector becomes a singleton. (3) A DRed-style retraction layer, 'requirements' (requirements.rs), carries callee-to-caller constraint backflow. It uses transactional per-owner sites (begin/stage/commit/abort), per-destination ordered folds with retained prefixes, four memo layers, a reverse-cone invalidation that clears derived bindings before refolding, and 'order receipts' that pin record field order across refolds. SummaryCall runs a tree-walking interpreter over KernelSummaryProgram at every call site; Invoke nodes re-run nested callee programs inline (solver.rs:2417-2766). Scheduling: work items start in Kahn topological order, with everything the topo pass cannot reach appended in id order (program.rs:1457-1577). Every binding change calls touch() -> schedule_variable(), which walks the whole equivalence class (linked list), each member's consumers and the transitive binding-dependents closure to re-queue consumers and mark requirement destinations dirty (solver.rs:4086-4134). Before every dequeue, refresh_requirements() invalidates and refolds dirty destinations (solver.rs:936). Occurrence provenance (syntax_selected, syntax_selected_here, call_syntax_selected) is computed inside the same loop and triggers touches too. After quiescence, outputs are resolved and frozen. receipt.rs and artifact_terms.rs then compute SHA-256 definition basis fingerprints, dependency graphs, currentness receipts (v14/v16/v17/v18 domains) and per-definition stable and runtime-erased term proofs; union members are ordered by their Debug-string rendering (legacy_checked_union_order, artifact_terms.rs:420). Correction to the brief: order.rs is not about field-order receipts. It derives List sort/then_by order chains and is negligible (1 of 2,950 NovyWave-verified samples). Field-order receipts live in requirements.rs:914-1270. runtime_facts.rs only packs definition facts into u32 columns. artifact.rs holds the work counters and output rows.
## essential_work
- One pass over checked expressions producing about one constraint per expression edge (TodoMVC 4,081 checked expressions and 352 checked calls; NovyWave 15,650 expressions and 1,821 calls).
- Equality/unification of function parameters and results, list/set/map items and HOLD/LATEST state types, including recursive cycles, which unification handles without iteration.
- Open-record requirement inference: a field access on an unknown value constrains it to have that field (row polymorphism), plus closed-record construction and missing-field errors.
- Tag-set typing for WHEN/WHILE/LATEST branch joins (polymorphic-variant-like unions), payload narrowing in patterns, and the language's structural widen/LUB where branches join.
- Polymorphism for unannotated FUNCTIONs: infer each definition once, generalize, instantiate at each call site. Where result types depend on the actual tag set of an input, this needs guarded/conditional constraints in the scheme.
- Arm reachability for SELECT, if the language guarantees that unreachable arms contribute no constraints.
- Diagnostics with spans: incompatible shapes, missing projections, unresolved shapes.
- Export of solved types per expression/output and public interfaces, with deterministic presentation order.
- For warm edits: per-definition caching keyed on definition content plus dependency interfaces (early cutoff). This is the only place retraction/incrementality belongs.

## from_scratch_design
Goal: solve each definition once, in dependency order, with monotone constraints and no retraction inside a batch.

1) Front end emits constraints directly from checked expressions in a single pass. There is no ComponentProgram linking, no residual frames and no summary bytecode. Each expression gets one type variable, or a direct TypeId when it is closed.

2) Types are hash-consed immutable nodes with TypeId(u32) in one arena. Header: {tag: u8, flags (has_var, open), a: u32, b: u32}; children live in one Vec<u32>. Records are (ShapeId, child ids), where ShapeId interns the field-name list sorted by u32 lexical rank. Record literals resolve their ShapeId and authored-to-canonical permutation at constraint-generation time, so interning is an O(f) FxHash with no sort. Tag sets are rank-sorted [(SymbolId, payload TypeId)] and are merged by merge-join. Unions are sorted by TypeId for identity. Authored field order and canonical display order are side tables used only at export, if the owner confirms order is not observable.

3) Variables use a union-find with path halving plus union by rank: parent Vec<u32>, a binding Vec<TypeId|NONE>, and level Vec<u32> for generalization. Open-object requirements are rows ({f: T | rho}, Remy/Wand). What merge_type_evidence does today is row unification with fresh row variables, so field accumulation needs no retraction. The occurs check uses a per-check mark or level adjustment and is otherwise deferred to generalization.

4) Directional flows (LATEST/WHEN joins, structural widen, value unions): use biunification in the style of Simple-sub (Parreaux 2020). Each variable keeps lower-bound and upper-bound lists; constrain(lhs, rhs) consults a hash set of already-processed (lhs, rhs) pairs, so each pair is propagated once. Cycles through HOLD/LATEST terminate through that cache, with no worklist re-execution. If the language's widen really is a LUB over records and tags, it is exactly the join of lower bounds, computed once at export or simplification time.

5) SELECT narrowing uses guarded, monotone constraints. Each arm registers a trigger on the selector variable's lower-bound tag set, and when tag A first enters that set the arm's constraints are instantiated once. An arm whose tag never enters contributes nothing. Nothing is withdrawn, because the lower bound only grows. This replaces today's non-monotone rule (all arms while unknown, one arm once the selector is a singleton).

6) Functions: compute call-graph SCCs with Tarjan and infer bottom-up. Each SCC is inferred once at level L+1. Generalization quantifies variables above L and simplifies the bound graph (Simple-sub simplification or co-occurrence analysis), so a scheme is a small type graph plus guarded constraints. At a call site the scheme is instantiated by copying it with fresh variables, O(scheme size). Closed-argument calls hit a memo table (DefId, [TypeId; n]) -> result TypeId; this is exact because the ids are hash-consed and the solve is batch, so no epochs are needed. Recursive calls inside an SCC use the monomorphic variable.

7) HOLD state: the scheme carries the state type variables, and each call instance instantiates them. No per-call-path solving is needed.

8) Diagnostics are recorded when a unification or biunification fails, carrying (expression span, call-site chain) as provenance. Nothing is re-solved.

9) Provenance: syntax_selected and call_syntax_selected become one bitset propagation over provider-to-consumer edges after solving, O(V+E).

10) Export: one zonk of all outputs with a global memo; union and field presentation order by rank.

11) Digests: FxHash/xxh3 structural hashes memoized per TypeId for in-process identity. SHA-256 only when writing a persisted artifact, computed once per term, not once per definition.

12) Warm edits: per-definition scheme cache keyed by (definition content hash, the dependencies' scheme hashes), with Salsa-style early cutoff. Only changed SCCs and their dependents are re-inferred, and the append-only arena keeps retained TypeIds valid. This is the only incremental layer.

Everything in today's (a) receipts machinery, (b) requirement retraction, cone invalidation, retained folds and reschedule epochs, (c) residual frames and per-call summary interpretation, and (d) interleaved provenance and per-definition SHA term proofs has no counterpart in this design.
## speed_ceiling
These are estimates, not measurements. TodoMVC has 4,081 checked expressions, 155 definitions and 352 calls. One constraint per expression edge is ~10k constraints; instantiations are ~352 x ~50 nodes, ~18k copies; closed-call memo hits remove about 35% of calls (measured closed share: 3,382 of 9,761). That totals ~30-40k union-find, intern and bound operations at 50-150 ns each (UI records with 10-30 fields dominate): about 2-6 ms for constraint generation plus solving. Today the same span costs prepare 60 ms + solve 280 ms = ~340 ms (measured: kernel_check_diagnostics prepare_ms 59-68, solve_ms 279-301 over 5 runs). NovyWave has 15,650 expressions, 1,389 definitions and 1,821 calls, so ~100-150k operations: about 8-20 ms, against 80 ms prepare + 230 ms solve today (measured: prepare 79-80, solve 229-231 over 3 runs). Verified intent adds a single memoized structural-hash export of ~1-3 ms, against 50 ms (TodoMVC) and 200 ms (NovyWave) today for packed_finalize plus receipts. A type-preserving warm edit with per-definition early cutoff should be under 1 ms of solver time. Where today's 10-100x comes from: (1) 20x problem inflation from per-call-path instantiation (82,358 variables for 4,081 expressions); (2) about 2x re-activation from unordered evaluation; (3) solver-side bookkeeping per activation (reschedule walks, requirement refolds, provenance walks, full resolves), about 1.6 us per activation (280 ms / 169,680); (4) per-hit interning costs.

## representation_critique
- structure: TypeTerm::Object / ObjectFields (term.rs:307-321, 2352) | critique: Identity includes authored field order, and both canonical and semantic orders are stored. Hashing uses semantic order, so {a,b} and {b,a} are different terms, and the order-sensitive merge and widen results force site-ordered folds and receipts. | better: ShapeId(rank-sorted names) plus a child id array for identity; authored order as a per-construction-site side table used only at export. | evidence: The Hash impl iterates semantic order; derived PartialEq compares canonical and semantic_order slices.
- structure: Consumers indexed per original variable (static CSR) plus equivalence-class linked lists | critique: Union does not merge consumer lists, so every touch or query walks every member. | better: Per-root intrusive consumer list concatenated in O(1) on union; per-root aggregate bits. | evidence: solver.rs:4086-4134, 4052-4062
- structure: VariableCell.requirement_base: Option<Option<TypeTermId>> plus binding | critique: A tri-state 'managed' flag splits the value between two slots, and every bind branches on it. It encodes retraction into the core cell. | better: A single binding per root; no managed state in a monotone solver. | evidence: solver.rs:40-49, 3100-3110, 3133-3146
- structure: About 13 parallel per-variable Vecs, grown for each contextual hole | critique: new_contextual_hole_term pushes 13 vectors per hole; the layout is cache-hostile, and holes are allocated per summary evaluation. | better: Compact union-find arrays (parent, rank/level, binding) only; provenance lives in the post-pass. | evidence: solver.rs:865-892
- structure: HashMaps with SipHash keyed by dense u32 ids | critique: Hashing cost where a Vec index would do; the kernel has no Fx hasher at all. | better: Dense Vec<Option<...>> indexed by variable, owner or target id; FxHash for pair keys. | evidence: solver.rs:326-395, term.rs:6 and 617
- structure: binding_dependents / binding_dependencies as sorted Vec<Vec<TypeVariableId>> | critique: Each edge change costs O(degree) and allocates per variable. - structure: Summary programs interpreted per call through closures and dyn FnMut | critique: Callee type-level programs are re-run for every call path, and SummaryValue mixes provenance flags into type values. | better: Generalized schemes (a type graph plus guarded constraints), instantiated by copying; provenance kept separate. | evidence: solver.rs:2290-2766, SummaryValue at 80-88
