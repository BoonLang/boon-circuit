## subsystem
Whole-pipeline representation census (source text to sealed MachinePlan / ProgramArtifact)
## purpose_summary
Today one verified compile builds about 62 distinct program representations and runs at least 27 structure-to-structure conversions. A from-scratch compiler needs 4: syntax tree, typed/resolved HIR, dataflow IR and MachinePlan, plus one type store and one interner. The chain runs like this. Source goes through CanonicalSourceBundleV1 (digested twice), then a retained token Vec, ParserLine Vec (cloned, then merged in 3 passes), ParserItem Vec, and the AST (statement tree plus expression arena). Next come ValidationIndex, item/owner indexes, per-expression SHA-256 route digests, ParsedSourceUnit, UnitSyntaxSnapshot (module names are rewritten as strings in the AST) and ProjectSyntaxSnapshot. The next leg goes from syntax to the kernel. Source-payload ABI types, value/callable surfaces, a per-compile builtin ABI and rich PreparedOwner/KernelOwnerProgramInput/KernelDefinitionFactsInput DTOs are all built as rich rows. They are then repacked into a text catalog, per-owner SHA basis fingerprints, a TypeTermArena, a PackedKernelProjectProgram, a PackedDefinitionFactsStore and a string-keyed link overlay. Inside the kernel: summary programs, residual modules and per-call-path invocation frames go into one global ComponentProgram (10,537 compiled call sites from 352 checked calls on TodoMVC). Then come solver state, the interface snapshot, DefinitionCodeStore and FrozenTypeStore, and SHA receipts. The checked side produces link layout and rows with rich boon_checked::Type values, then CheckedProgramFields inside 6 wrapper types. It also produces checked-image publication/authority/handoff/pairing receipts and a parallel packed KernelSemanticInputV1. The semantic side builds 7 separate graphs (execution, resource, reactive, lowering, storage, view, memory), each with its own IDs, digests and dependency rows. These are merged into CanonicalProgramCoreV2, followed by execution handoff hashes, a dependency manifest plus request graph, a sealed semantic image and a digest. VerificationManifest and ContractVerifiedProgram come next, then ErasedProgram, which is the core moved plus 3 digests and is verified twice. The backend builds slots and row expressions (SHA-256 per interned node), a DocumentPlan inflated by per-call-site inlining (64,482 document expressions from 4,536 IR expressions on TodoMVC) and a whole-plan clone. Finally the MachinePlan is sealed (41-check verify_plan plus a full binary encode and SHA). The child-program path adds a CBOR encode plus SHA and runtime Metadata. into_lowering_parts (boon_semantic/src/lib.rs:1068) keeps only CanonicalProgramCoreV2 and 3 digests, so every other semantic graph, the dependency manifest, the semantic image and all receipts are dead once the IR exists. None of the digests reach MachinePlan. Only about 25% of NovyWave verified time (464 of 1,870 ms) is essential work: a type solve (itself inflated by per-call-path expansion) plus core IR and plan construction. The rest goes to building, converting, validating and hashing intermediate representations. Measured on NovyWave verified: about 216 ms of representation building before the solve, about 364 ms of kernel/checked publication after it, and 780 ms of semantic phases. Each compile makes 7.46M allocations (1.33 GB), which is 477 allocations per checked expression.
## essential_work
- Read the package's source units (8 files for TodoMVC and NovyWave) and compute one fast content hash per unit as a cache key.
- Lex and parse each unit into a syntax tree with spans. That is 73,591 tokens / 17,721 expressions on NovyWave and 19,207 / 4,858 on TodoMVC.
- Resolve module-qualified names and item references across units, and bind builtins from a static library/renderer ABI.
- Infer types for unannotated FUNCTIONs: structural records with requirements, tag/variant sets, lists, flow modes (TickPresent/PresentOrAbsent), FLUSH, and tag narrowing in WHEN/WHILE arms. This includes whatever call-site specialization the language semantics genuinely require.
- Produce complete diagnostics with source spans, plus an editor type projection generated on demand.
- Compute demand/reachability from program roots (outputs, sources, states, effects).
- Lower to a reactive dataflow graph: SOURCE, HOLD, LATEST, THEN, WHEN/WHILE, LIST operations and projections, OUT/PASS contextual materializations, list-row scopes, static owners, pulse batches and activations, state update arms and host effect schedules.
- Assign storage (scalar/list slots, byte banks, persistence paths) and build dirty/commit/delta plans and operation regions.
- Build the document/render template plan (constants, templates, view bindings, initial patch batch).
- Emit the MachinePlan. Compute one artifact hash only when the plan is persisted, transmitted or loaded from an untrusted source.
- For warm edits: per-unit parse reuse and per-item/SCC type result reuse keyed by content plus dependency interface hashes.

## from_scratch_design
The minimal chain is Source -> AST -> Typed HIR -> Dataflow IR -> MachinePlan, backed by one global Interner and one TypeStore.

(1) Loader. One xxh3 hash per unit serves as the cache key. A cryptographic bundle digest is computed only if an artifact is persisted.

(2) Parse, per unit (and parallel if wanted). A layout-aware lexer streams tokens into a recursive-descent/Pratt parser. The AST is a flat arena, Vec<Node{kind:u8, flags:u8, span_start:u32, span_len:u32, a:u32, b:u32}>, with a children Vec<u32>. Identifiers, paths, tags and numbers are SymbolId from the single interner. An item table per unit is built in the same pass. Policy checks (list capacities, reducer style, hidden identity, pipeline and match patterns) run inline. Tokens, lines, items, route digests and module rewrites are not retained. The editor re-lexes on demand.

(3) Resolve. Module scope tables are FxHashMap<SymbolId, ItemId>. A per-node Res side table (Vec<Res>) records resolutions. Builtins/renderer ABI come from a static, process-lifetime table of type schemes built once. SOURCE payload types are resolved directly into TypeIds.

(4) Type check. The TypeStore is hash-consed: nodes Vec<TypeNode>, map FxHashMap<TypeNode, TypeId>. Records are sorted (SymbolId, TypeId) slices in a side buffer. Tag sets are sorted SymbolId slices or bitsets. Flow modes and requirements are node attributes. Unification uses union-find over TypeVar. Constraints are generated per item, and items are solved bottom-up over call-graph SCCs, then generalized. Call sites instantiate schemes. Where Boon semantics require call-site-specific results (WHEN/WHILE syntax-selected arms), a memo keyed by (ItemId, arg TypeId tuple, dependency epoch) returns cached results, per AGENTS.md's own 'exact semantic input tuples' rule. Output: expr_type: Vec<TypeId>, a scheme table and a diagnostics Vec. The editor type projection (hints, render slot reports, function tables) is computed lazily from HIR plus types. There is no rich Type, no receipts, no checked image and no pairing. Field-order handling depends on the owner's answer.

(5) Dataflow lowering. One pass from roots (reachability) over the typed HIR emits the IR: Vec<IrNode{op, inputs: Range<u32>, ty: TypeId, scope: ScopeId, owner: OwnerId}>, plus tables for resources (SOURCE/HOLD/LIST), pulse batches, activations, state update arms, effect schedules, materializations and view bindings. Functions remain shared bodies. They are specialized only for OUT/PASS context or list-row templates, keyed by (fn, context) tuple. Resource, reactive, storage, view, memory and pulse-fusion analyses are passes that write side tables indexed by IrNodeId. They are not separate graphs with their own IDs, digests or dependency rows. Invariant checks run under debug_assertions and in tests.

(6) Plan. Slot layout, regions, dirty/commit/delta plans and persistence paths. The document is templates plus a shared function table plus a constant pool. Row expressions go in an arena interned with FxHash. There is no clone and no verify for in-process plans. verify_plan is kept for decoded or untrusted plans. The artifact hash is one streaming hash over the final binary encoding, computed only when stored or sent. Runtime Metadata indexes are emitted by the compiler into the plan.

(7) Incremental. Keep the per-unit parse memo (exists: session.rs:837-877). Per item: body hash plus the dependency schemes' hashes decide reuse of the item's type results, with red/green over SCCs. IR and plan are rebuilt for the dirty cone, or wholesale if a cold IR+plan build takes ~20-40 ms.

Mapping of current representations: KEEP (4 plus store): AST (compacted), TypeTermArena as the single TypeStore, CanonicalProgramCoreV2 as the IR (with TypeIds and SymbolIds), MachinePlan. MERGE: ProjectSyntaxSnapshot/UnitSyntaxSnapshot/ParsedSourceUnit into the package AST. Item/owner indexes into the AST item table. PackedKernelProjectProgram, PackedDefinitionFactsStore, KernelSemanticInputV1 and CallCatalog into the HIR plus side tables. KernelInterfaceSnapshot, DefinitionCodeStore and FrozenTypeStore into the scheme table and expr_type. The 7 semantic graphs, VerifiedSemanticIntent, OutNet, contextual materializations and pulse fusion into IR lowering passes. ErasedProgram into the IR. The 4 interners into one. DELETE: retained tokens/lines/items, ValidationIndex as a separate pass, route digests, module string rewrite, second bundle digest, PreparedOwner/KernelOwnerProgramInput/KernelDefinitionFactsInput, per-compile builtin ABI projection, text catalog rediscovery, basis fingerprints, string-keyed link overlay, the per-call-path ComponentProgram, receipts (V17/V3/V18), KernelCheckedLinkLayout/Rows, CheckedProgramFields and its 6 wrappers, checked-image publication/authority/handoff/pairing, ArtifactTypeModule runtime flow terms, execution proofs/image routes, execution handoff V5, dependency manifest V7, SealedRequestGraphSnapshot, SealedSemanticImageV5, SemanticProgramDigest, VerificationManifest/ContractVerifiedProgram, duplicate IR verify and the plan clone. DEBUG-ONLY: verify_plan on trusted plans, IR invariant checks, order-chain parity oracle, compiler-sample pretty-JSON export, editor type tables (on demand).

Counts: 62 representations today vs 4 (+2 shared stores); at least 27 conversions vs 3; an estimated ~130 whole-program traversals vs ~10-15; 5 type encodings (rich Type, TypeTermArena, FrozenTypeStore, ArtifactTypeTermV1, DataTypePlan/PlanValueType) vs 1 (+1 plan value encoding); 3 call-expansion passes (kernel frames, OutNet, document inlining) vs 1 memoized specialization; 4 string interners (parser SharedParserSymbols, kernel ProjectTextSnapshot, boon_contract text catalog, document names) vs 1.
## speed_ceiling
All figures are estimates for the clean design, single thread, on the same i7-class machine. Parse: NovyWave is 433 KB / 73,591 tokens; at a conservative 50-100 MB/s that is 4-9 ms (today 64). TodoMVC is 103 KB, so 1-2 ms (today 18). Resolve: 1-3 ms NovyWave, <1 ms TodoMVC. Type check: NovyWave has 17.7k expressions, 1,821 calls and 552 callables. At ~1-2 us per expression for HM-with-rows plus scheme instantiation, that is 20-45 ms (today 456 ms diagnostics). TodoMVC has 4.9k expressions but heavy tag sets (140,701 variant rows today) and call depth 12. With 352 call-site instantiations plus memoized argument tuples instead of 10,537 call paths it should take 10-30 ms (today 368). IR lowering plus analyses: 16k NovyWave nodes over ~6 side-table passes is 10-25 ms (today semantic 780 + IR 25); TodoMVC 3-8 ms (today 162). Plan: NovyWave 10-25 ms (today backend 217 + seal 66). TodoMVC 5-10 ms: a shared-function document would have ~5-8k expressions instead of 64k (today 85 + 91). Totals: TodoMVC diagnostics ~15-35 ms (budget 75, today 390), verified ~25-55 ms (budget 300, today 800). NovyWave diagnostics ~30-60 ms (budget 250, today 526), verified ~60-120 ms (budget 1000, today 1,870). Counter <3 ms (budget 10/50). Warm TodoMVC type-preserving edit: re-parse one unit (~0.5-1 ms), recheck the dirty SCC cone (~1-5 ms), re-present diagnostics, so ~3-8 ms against the 16.7 ms budget. Warm verified preview: rebuild IR plus plan ~10-20 ms against the 100 ms budget. This puts the design within 2-3x of the brief's ~1M lines/s parse and ~100k+ lines/s check reference. Today's gap is roughly 10x at parse, 15-20x at typecheck (TodoMVC runs 3,576 lines in 368 ms, about 10k lines/s) and 30-60x at the back half, where most time goes to conversions and proofs.
